# Architecture

```
src/
  main/           Electron main process (Node.js)
  preload/        IPC bridge (contextBridge)
  renderer/       Vue 3 frontend
  shared/         Shared IPC contract + ambient types (imported by all three)
```

## Process Model

```
Renderer (Vue)  --ipcRenderer.invoke-->  Preload (bridge)  --ipcMain.handle-->  Main (Node)
                <--webContents.send----                                          |
                                                                                 |
                                                              DownloadManager    |
                                                              electron-store     |
                                                              ffmpeg-binaries    |
                                                              smotret-anime API  |
```

For the per-domain IPC router split and the disposable subscription contract, see [IPC](./ipc.md). For the renderer-side architecture (Pinia stores, composables, components folder layout), see [Renderer](./renderer.md).

## Offline mode (#567)

`OfflineService` (`src/main/services/offline/`) owns the offline state, and `fetchWithTimeout` refuses every request while it reports offline, in either mode, with an `OfflineError` that `isNetworkError` classifies, so every write path that queues on a network error keeps queueing. Only the probe passes `bypassOffline`. What doesn't go through `fetch`, and background work that shouldn't even be scheduled, is gated on `isOffline()` directly:

| Gate | Where | While offline |
|---|---|---|
| Renderer http(s) | `lib/offline-request-gate.ts`, installed next to `installShikimoriReferer` | `onBeforeRequest` cancels it |
| Updates | `ipc/app.ipc.ts` | `UPDATE_CHECK` / `UPDATE_DOWNLOAD` broadcast `{ status: 'error', error: 'Offline' }`; a due daily check is skipped at boot and runs on the first online edge instead (the router's own `offlineService.onChange` listener) |
| Syncplay | `syncplay.ts` (`setOfflineCheck`, `suspendForOffline`, `resumeAfterOffline`) | Every socket open is refused with `SYNCPLAY_OFFLINE_ERROR`; entering offline drops an open session without a retry; back online a dropped session reconnects if `autoReconnect` |
| Auto-download | `auto-downloader.ts` (`isOffline` dep) | Every tick returns before the re-entrancy lock |
| Shikimori background | `services/shikimori-sync` (`isOffline` dep), `ipc/shikimori.ipc.ts` | The drain (and so the 60 s timer) and the details prefetch return early; `refreshShikimoriRatesInBackground` too. Writes keep queueing |
| First-launch binaries | `ensureFfmpeg` / `ensureFpcalc` (`isOffline` argument) | An install that would download is skipped (resolves `''`, no error modal) and retried by the online kick-off. One that the offline switch interrupts mid-way — an `OfflineError`, e.g. between the ffmpeg and ffprobe archives, or, once offline, a timeout or a network-coded error (`isTransportError`; a bare `TypeError` is a bug and still fails) — sends `status: 'deferred'` instead of `'failed'` and is retried the same way. Boot and the retry share one in-flight install per binary (`lib/binary-installs.ts`, `singleFlight`), so two never extract into the same directory. A merge in that same session still sees ffmpeg as unavailable — the kick-off's retry doesn't call `ffmpegStatus.refresh()`, so `ffmpegStatus` keeps the boot check — as after any failed first install, until Prepare for offline (#592) or a restart refreshes it |
| Downloads | `download-manager.ts` | See its row above |

What the views show offline (#568): `get-anime-cache` drops its 24 h TTL and `get-anime` answers from the cache without calling the API (`OfflineError` with no entry); `shikimori:get-calendar` and `shikimori:get-friends-activity` serve the shikimori-sync service's in-memory snapshots ([Shikimori › Offline snapshots](./shikimori.md#offline-snapshots-568)). The renderer side is in [Renderer › Views offline](./renderer.md#views-offline-568).

The `test/net-adoption-guard.test.ts` AST guard pins it: no bare `fetch` outside `lib/net.ts`, `net.createConnection` only in `syncplay.ts`, `autoUpdater.` only in `ipc/app.ipc.ts`, and `bypassOffline` only in the probe.

## Prepare for offline (#592)

`PrepareOfflineService` (`src/main/services/prepare-offline/index.ts`) runs an ordered list of steps registered with `registerStep(step)`, one at a time. It is single-flight (a second `start()` returns the running `runId`) and cancellable (an `AbortController`; Cancel aborts the running step at its next `ctx.signal` check and marks the rest `skipped`, "Cancelled").

- **The step contract:** `{ id, label, requiresNetwork, isAvailable(), run(ctx) }`. `run` reports `{ done, total, message }` through `ctx.progress` and returns `{ status: 'ok' | 'warning' | 'failed' | 'skipped', details[] }`; a detail can carry an `animeId`, which the panel links to the title's page. A step whose `isAvailable()` says no is reported `unavailable` with its reason and never runs. While `offlineService.isOffline()`, every `requiresNetwork` step is skipped with "Offline: connect to run this step" and the local ones still run. A step that throws is `failed`, and the next steps still run.
- **Progress** goes out on `EVENT_CHANNELS.PREPARE_OFFLINE_PROGRESS` as the whole `PrepareOfflineRun` (each step's state, `done / total`, status, details) after every change. The end of a run stores `prepareOfflineLastRun` (per-step status, no details).
- **Steps** (`steps/`, wired in `src/main/index.ts` in this order):

  | Step | File | Network | What it does |
  |---|---|---|---|
  | ffmpeg, ffprobe and fpcalc | `binaries.ts` | only to download | `ensureFfmpeg` / `ensureFpcalc` (single-flight, so it joins a boot install), then `-version` on each; a failing binary is deleted and downloaded once more behind the repair gate ([FFmpeg › Prepare for offline](./ffmpeg.md#verification-and-repair-prepare-for-offline-592)); ends with `ffmpegStatus.refresh()` |
  | Shikimori rates | `shikimori-rates.ts` | yes | "Not logged in" when logged out; `drainNow()`, then `refreshRates({ keepQueued: true })` (a title with a live queue entry keeps its cached rate; "N edits still waiting to sync"), then `prefetchShikimoriDetails()` |
  | Library metadata | `metadata.ts` | yes | S2's whole cache scope (`isCachableAnime`: starred, downloaded, watched in the last 90 days), two titles at a time: `getAnime` → `animeCacheService.refreshAnimeDetail` (awaits the poster, repairs a `posterCached` flag with no file), then `getEpisodesBatch` → `updateEpisodes`. A failed title or poster is a `warning` detail |
  | Downloaded episodes | `local-integrity.ts` | no | Each `downloadedEpisodes` entry: the file by the player's name rule (`lib/episode-video-path.ts`, hot then cold), size > 0, and a duration from `ffprobe -show_format` (`lib/probe-duration.ts`, 15 s, two at a time); `.part` files no queue item owns. Reports only |
  | Shared Libraries | `attached-integrity.ts` | no | Every manifest item of each available attached library through S7a's `checkItem` (containment, existence, size); unplugged is "Drive not connected". Not available with no library attached |
  | Sync owned or claimed libraries | `library-sync.ts` | no | S9's `runAll('prepare')`, one line per owned or claimed library from its `SyncRunResult` (`drive` / `driveReason`, `shikimori` / `shikimoriReason`); a line is the worse of its two parts, a skipped Shikimori leg is `ok`. Foreign and Videos-only libraries are only counted. Not available with no library attached |

The renderer side is `stores/prepare-offline.ts` and `components/settings/PrepareOfflinePanel.vue`, mounted in `App.vue`, opened from Settings → General and from the missing-ffmpeg banner ([Renderer](./renderer.md)).
