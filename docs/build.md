# Build

```bash
npm run dev          # Development with hot reload
npm run build        # Compile to out/
npm run pack:win     # Build + package Windows portable exe
npm run pack:linux   # Build + package Linux AppImage
npm run pack:mac     # Build + package macOS zip
```

Dependencies: electron-vite bundles everything except electron-store (excluded from externalization to handle ESM). FFmpeg + ffprobe downloaded at runtime by `src/main/ffmpeg-binaries.ts` (native `fetch` against the `ffbinaries-prebuilt` GitHub releases).

## Artifact naming

`build.artifactName` is `Anime-DL-${version}-${arch}.${ext}` for every target except Windows **portable**, which overrides to `…-portable.exe` (`build.portable.artifactName`) — portable and NSIS both produce `.exe`, and without the suffix the second build overwrote the first in `dist/` (#189).

## macOS signing + notarization (#189)

The mac build is signed with a Developer ID Application certificate and notarized so Gatekeeper accepts it and `electron-updater` (Squirrel.Mac) can auto-update. Config lives in `package.json` `build.mac`: `hardenedRuntime` + the Electron JIT entitlements in `build/entitlements.mac.plist` (required or the signed app crashes at launch), `notarize: true`.

Credentials come from repo Actions secrets, mapped to the env vars electron-builder/@electron/notarize expect by the **"Set up macOS signing & notarization"** step in `release.yml`:

| Secret | → env | Content |
|---|---|---|
| `ANIME_DL_CSC_LINK` | `CSC_LINK` | base64 `.p12` (Developer ID cert + key + Apple G2 intermediate) |
| `ANIME_DL_CSC_KEY_PASSWORD` | `CSC_KEY_PASSWORD` | `.p12` password |
| `ANIME_DL_APPLE_API_KEY` | `APPLE_API_KEY` (as a **file path** — the step writes the `.p8` to `$RUNNER_TEMP`) | App Store Connect API key |
| `ANIME_DL_APPLE_API_KEY_ID` | `APPLE_API_KEY_ID` | key ID |
| `ANIME_DL_APPLE_API_ISSUER` | `APPLE_API_ISSUER` | issuer UUID |

Scope: **only `release.yml`** (version-bump pushes to main) signs and notarizes. PR builds (`check.yml`) never see the secrets and stay unsigned — deliberate, so fork-triggered runs can't touch signing material. If the secrets are absent the release build degrades gracefully: unsigned without the cert, signed-but-not-notarized without the API key.

Verification on a signed release: `codesign -dv --verbose=2`, `spctl -a -vv` ("Notarized Developer ID"), `xcrun stapler validate` against the unpacked `.app`.

## Publishing a release (#365)

A version bump landing on `main` runs `release.yml`: `check-version` decides whether the version has shipped, `build` packages all three platforms into `dist-{linux,win,mac}` artifacts, and `release` turns those into a GitHub release. The order inside `release` is **draft → upload → verify → publish → tag**, and every one of those four arrows exists because of a specific way v4.6.92 and v4.6.93 were lost.

**The release is created as an explicit draft.** A draft is not public and — this is the part that matters — **does not create the git tag**. GitHub creates the tag at the `--target` commit only when the release is published, which is the last step in the job. So a run that dies anywhere in the middle leaves a draft, no tag, and a version number that is still free. The step is idempotent: "Re-run failed jobs" reuses the draft an earlier attempt left behind rather than failing on it, and re-uploads only what is missing.

**Uploads are one file per `gh release upload`, each with its own bounded retry** (`scripts/release-assets.mjs upload`). This replaces `softprops/action-gh-release`, which fires every file at GitHub concurrently. On v4.6.93 that was 13 simultaneous uploads; one large binary came back with GitHub's own `Error saving asset` about ten seconds in, and the four other large binaries still in flight were abandoned with no log line at all. The eight small files (344 B – 143 KB) had already landed. Serialising the uploads removes the fan-out that correlates with the failure, and the per-file retry means one file's 5xx can neither abort the others nor end the step.

Serialising also makes a *stalled* upload worse than it was, which is why there are three bounds rather than one. The retry loop bounds errors that come back; a 15-minute `timeout` (`SIGKILL`) on each `gh` call bounds one that doesn't, which under the old fan-out only cost that file and now holds up every file behind it; and a 20-minute budget across the whole batch stops a file being *retried* once there is no longer room for another attempt, so a hang gives up after roughly one timeout and the script names the file it was stuck on. `timeout-minutes: 30` on the `release` job is the backstop behind all three — it should never be what fires, and if it is, `report-failure` still files the issue. The 15-minute figure is well past the slowest upload actually observed here: ~11 minutes for the 138 MB AppImage.

The budget treats a file's first attempt and its retries differently, and the asymmetry is the whole point: refusing to start a file guarantees it is missing from the release, while starting it only risks the 30-minute backstop that exists to catch exactly that. So a first attempt runs unless the 20 minutes are genuinely spent, and only a retry asks whether another full-length call could still fit. One guard for both cases reduces to "refuse anything new after 5 minutes" at these numbers, which fails a healthy release: the set is ~722 MB, and at the ~1 MB/s the real failing run managed, a complete upload takes ~11 minutes. `test/release-assets.test.ts` pins that run — 13 files, realistic durations, an injected clock — against the budget.

**Everything that arrived has to be attached, and all three updater feeds have to have arrived.** That is what `scripts/release-assets.mjs verify` promises, and it is worth stating precisely, because it is weaker than "the release is complete". The check reads the release back and compares its asset names against the files in `artifacts/`; the publish step runs only if the two sets match exactly. An asset counts as attached only if GitHub reports `state: "uploaded"` — the asset record is created before the bytes land, so a half-written asset sits on the release under exactly the right name and is treated as missing. Missing names are listed and fail the job. So do extra names — the release job is the only thing that should write into this draft, so an asset that did not come out of the build means something else published into it, which is why the `Package` step passes `--publish never`. An empty artifact set fails too: an empty release that publishes looks like a shipped version and offers `electron-updater` nothing.

The limit of that comparison is that both halves of it are computed against whatever `download-artifact` put in `artifacts/`, so a platform that produced *nothing* compares clean: `upload-artifact` runs with `if-no-files-found: ignore`, so a matrix leg whose `dist/` globs stop matching uploads nothing, the release job downloads nothing for it, and a release with no Windows binaries in it would otherwise pass. The floor under that is `latest.yml`, `latest-mac.yml` and `latest-linux.yml` — the three `electron-updater` feeds, one per platform, produced by any leg that ran. All three must be in `artifacts/` before the comparison counts for anything, and a missing one is reported by name, because publishing without it silently 404s the update check for everyone on that platform. It is a proxy for "all three legs produced output", not a per-platform manifest: a leg that produces its feed and loses one binary is caught by the comparison, not by the floor. Fixtures in `test/release-assets.test.ts` pin every case above, including the real v4.6.93 set of 13 built versus 8 attached.

**Why the draft was left stranded before.** `softprops/action-gh-release` already used the draft-first shape — `const draft = prerelease === true ? config.input_draft === true : true` — but it flips `draft: false` from `finalizeRelease()`, which runs only after every artifact has uploaded. An upload failure therefore meant finalize never ran, and both versions were left permanently draft with eight small files and none of the five ~100–140 MB binaries. The shape was right; what was missing was a step that says *why* the draft may be left, and a retry so it usually isn't.

The filename-collision theory (a retried upload colliding with its own half-written asset, fixed by `--clobber`) was tested and does not hold. The step already ran with `overwrite_files: true`; the v4.6.93 failure was attempt 1 against a release with no assets yet; and on the v4.6.92 attempt 2, where duplicates genuinely did exist, every duplicate small asset re-uploaded in under a second. The action handles a 422 `already_exists` explicitly by deleting the conflicting asset and retrying, so a collision cannot surface as `Error saving asset`.

**`check-version` asks origin, not the local clone.** The guard is `git ls-remote --exit-code --tags origin "refs/tags/$TAG"`. The `git rev-parse "v$VERSION"` form it replaced was a no-op: `actions/checkout` runs `git fetch --no-tags --depth=1`, so the working clone has no tags to parse and every run answered `should_release=true` regardless. It went unnoticed because the answer was right by accident — a version bump lands once. Now that the tag is created only by a successful publish, a tag on origin means "this version shipped" and nothing else, which is what makes the guard worth having.

## Release failures (#320)

**The macOS keychain failure is fixed upstream.** It was an electron-builder bug, not a secrets problem: `importCerts` passed the `.p12` import password to `security set-key-partition-list -k`, which expects the *keychain's* own randomly generated password. macOS ≤ 26.5 never validated `-k`, so the mismatch was invisible until the runner image roll (`20260707.563` → `20260828.587`) brought 26.6.2, which validates and rejects it — the whole story is on [#327](https://github.com/mikkerlo/anime-downloader/issues/327) and [#332](https://github.com/mikkerlo/anime-downloader/issues/332). The v26 backport shipped in **app-builder-lib 26.16.1**, so `package.json` pins `electron-builder` to exactly `26.16.1`. Keep it exact — not because a caret is unsafe in principle (`^26.16.1` resolves forward to the fix today), but because nothing gates a regression: `check.yml` packages `zip` with `--publish never` and never touches the signing path, so a later in-range `26.x` that broke the same call would reach a release unexercised. If it is ever widened, the range must admit nothing below `26.16.1`: npm resolves a range to the `latest` dist-tag whenever `latest` satisfies it, in preference to any higher in-range version, which is why `^26.8.1` — the range this replaced — resolved backwards onto `26.15.3`. As of 2026-09 `latest` is `26.15.3`, the fix ships only on the `v26` tag, and `26.15.4` through `26.16.0` are unfixed as well. The mac-only retry leg, the `$TMPDIR` keychain sweep and the `if: matrix.platform` split in `release.yml` all existed only for this bug and are gone; all three platforms now run the same plain `Package` step. `strategy.fail-fast: false` stays, so one platform failing does not cancel the other two — a partial matrix still shows which targets are broken, and the release job needs all three artifacts regardless.

When a release build fails, the `report-failure` job opens an issue naming the version and linking the run (built-in `GITHUB_TOKEN`). The title is version-scoped and the job looks for an open issue with that exact title first, so re-running the failed jobs — which re-runs `report-failure` under the same run id — appends a comment with the new run URL instead of filing a duplicate. Before this job existed the failure was silent — `release` was simply skipped — which is how v4.6.56 was permanently lost.

**A re-run cannot fix a cause that lives in the repo.** A re-run replays the workflow file *and* the repo state from the original commit — `GITHUB_SHA` is pinned — so no fix landed on `main` afterwards reaches it. That makes the first question "where does the cause live?", not "is a newer release out?". A transient cause (upload blip, registry timeout) is recoverable by re-running; a bad dependency, build break or workflow error is not, and has to be fixed on `main` and shipped. If the fix touches `package.json` it cuts a release on merge, so leaving the version field alone while changing anything else in that file recovers the untagged version without spending a new number — the `paths:` filter matches `package.json`, not the version key. That is the route taken for the untagged `v4.6.71` (#332).

**A late rerun is not always safe.** For the transient class, the publish step passes `--latest` (preserving the `make_latest: true` the old action defaulted to, which is what `electron-updater` reads `latest.yml` from), so re-running an old failed release build *after* a newer version has shipped publishes the older version last and marks **it** Latest — offering live users a downgrade through `electron-updater`. Check `gh release list` first: rerun only if nothing newer has been released. If something newer exists, leave the version gap — the commit's code ships in the later release anyway, and the abandoned draft can be deleted.
