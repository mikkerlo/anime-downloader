# FFmpeg

Both `ffmpeg` and `ffprobe` are auto-downloaded on first app launch via `src/main/ffmpeg-binaries.ts` to the app's userData directory. Platform is auto-detected. The two `.zip` archives are fetched (via `fetchWithTimeout` in `src/main/lib/net.ts`, a timeout wrapper over node's built-in `fetch`) from `github.com/ffbinaries/ffbinaries-prebuilt/releases/download/v6.1/`, extracted **in-process** by `extractZip` in `src/main/lib/unzip.ts` — no external extractor is required on any platform — and `chmod 0o755`'d into `app.getPath('userData')/ffmpeg/`. ffprobe is required for duration probing (used in merge progress calculation).

**Not bundled; needed per PC for MKV from a Shared Library (#578, epic #563 owner decision 1).** ffmpeg isn't shipped with the app. Every PC that plays from a Shared Library downloads ffmpeg, ffprobe and fpcalc once while online, as above, or through Prepare for offline (S12 #592). An `.mkv` from a drive plays through the MSE remux, which needs ffmpeg; an `.mp4` with its `.ass` sidecar plays without it. Opening a library calls `checkFfmpeg()` (`ffmpeg -version`), and with ffmpeg missing and `.mkv` items on the drive, the open result carries `ffmpegMissing: { mkvCount }`: the open flow and the library's section in Library → Shared Libraries show a warning, and `.mkv` Play buttons are disabled with the reason as a tooltip. The renderer re-reads `ffmpeg:check` on window focus and before each `.mkv` Play, so the warning clears once ffmpeg is installed. Every ffmpeg / ffprobe the player spawns for a file under an attached root gets `spawnPathFor(path)`, the `\\?\` form on Windows — see [Shared Library](shared-library.md#opening-a-library-578). The build each OS downloads is `detectFfmpegPlatform`'s: `win-64` on Windows, `linux-64` / `linux-32` / `linux-arm-64` / `linux-armhf-32` on Linux, and `macos-64` on every Mac, an x86_64 build that Apple Silicon runs under Rosetta; see [Shared Library › Per-OS limits](shared-library.md#per-os-limits).

Extraction used to shell out to the system `tar` with `-xf`, which reads zip only when `tar` is bsdtar/libarchive. That holds on macOS and Windows 10 1803+ and not on GNU-tar Linux, so first-launch install failed outright on most Linux boxes (#469). ffbinaries publishes no tar-format asset for any slug we request, so the fix was to read zip ourselves: `extractZip` scans the end-of-central-directory record, walks the central directory, and streams each entry through `zlib.createInflateRaw()` (method 8) or straight through (method 0), rejecting any other compression method. It covers stored + deflate only — no zip64, no encryption — which is sufficient for every ffbinaries asset and for the nested Chromaprint Windows zip (see `docs/skip-detection.md`).

Each entry is written to `<name>.partial`, checked against the uncompressed size recorded in the central directory (plus CRC-32 where `zlib.crc32` is available, Node ≥ 20.15), and renamed only on success; any failure unlinks the `.partial`. That matters because `ensureFfmpeg` treats "both binaries exist" as "installed" and never re-downloads, so a truncated binary left at its final path would be accepted by every later launch. Entry names that escape the destination directory are refused. The Unix mode recorded in the high 16 bits of an entry's external-attributes field is carried over, masked to the permission bits (`& 0o777`) — a wider mask would copy setuid/setgid/sticky out of a fetched archive, and no asset we request sets them nor needs them (#472). The archive's recorded modification time is restored too, so an extracted binary carries the upstream build's time rather than the install time, as it did in the `tar` era: the `0x5455` extended-timestamp extra field (Unix seconds, UTC) is preferred over the DOS date/time words, which is what libarchive does and what the two assets we fetch require — ffprobe's zip records DOS `2023-11-11 13:55:58` against UT `2023-11-11 05:55:58Z`, so reading the zone-less DOS words instead would be 8 hours off. The DOS words are the fallback, read as local time, and an entry that records neither is left alone rather than stamped 1980. The DOS fields are wider than the clock — hours run to 31, minutes to 63, the seconds field to 62 s, the day to 31 — and the `Date` constructor carries any overflow into the next unit, so `2023-11-11 31:63:62` would land as `2023-11-12 08:04:02`; both words are range-checked and the constructed day is compared back against the recorded one, and an entry that fails either is left alone rather than stamped a plausible-looking wrong time. The `utimes` runs on the `.partial` before the rename (which preserves mtime) and is non-fatal — a correct binary with a wrong timestamp beats a failed install (#475).

`extractZip` throws only the structural half of the message (archive basename + problem) because it is shared with `fpcalc-binaries.ts`; `fetchComponent` adds the `ffmpeg:` prefix and the recovery sentence ("Delete the ffmpeg binaries in Settings → Debug and relaunch to retry", or a report link for an unsupported compression method). That text rides the `message` field of `EVENT_CHANNELS.FFMPEG_DOWNLOAD_PROGRESS` on a `'failed'` status into the settings store's `ffmpegError`, which keeps the first-launch overlay up with the reason and a Dismiss button instead of silently hiding it.

Two things make that modal readable for the failures that are not extraction failures. `ensureFfmpeg`'s catch runs every message through `describeInstallFailure`, which passes through anything already starting `ffmpeg:`/`ffmpeg ` (the extractor wrap, the `!res.ok` text, the binary-not-found and unsupported-platform throws) and prefixes everything else — an offline `fetch` rejects with the bare two words `fetch failed`, which would otherwise be the modal's entire contents. That default prefix blames the connection, so the local failures are taken out ahead of it (#472): `isFilesystemError` tests for `syscall` on the error itself, which Node sets for a failed syscall — `ENOSPC` from the write stream, `EACCES`/`EPERM` from `mkdirSync`/`mkdtempSync`, a failed `rename` — while an offline `fetch` rejection is a `TypeError` keeping its errno detail on `cause`. Those get "Check free disk space and permissions on the temp and app data folders" instead — both folders, because the two halves of an install live on potentially different filesystems: `fetchComponent` makes its scratch directory with `fs.mkdtempSync` under `os.tmpdir()` and `downloadToFile` writes the ~29 MB archive there, while only the extract and `fs.mkdirSync(dest)` land under `app.getPath('userData')`, and on distros where `/tmp` is a size-capped tmpfs naming just one of them points the user at the wrong disk (#472). And `describeExtractFailure` applies the same test first, because `extractEntry` rethrows the raw fs error and an `ENOSPC` while inflating the ~79 MB of binaries is no more "probably truncated" than it is a network problem. Only the broadcast text is rewritten; the original error is still rethrown, so `cause` chains are intact. And the unsupported-platform check now sits *inside* the `try`, below `sendProgress`: it used to throw above both, making it the one install failure the renderer was never told about at all.

Available video codecs for merge (filtered by what ffmpeg reports):
- `copy` — no re-encode, fastest
- `libx265` — H.265 CPU
- `hevc_nvenc` — H.265 NVIDIA GPU
- `hevc_amf` — H.265 AMD GPU
- `hevc_qsv` — H.265 Intel QuickSync
- `hevc_videotoolbox` — H.265 macOS hardware

Merge progress is calculated from `timemark / probed_duration` (works for all codecs). Sequential merging enforced: one ffmpeg at a time across the download queue, Scan & merge and Shared Library export merges, through the ffmpeg mutex (see "The ffmpeg mutex and export merges (#576)" below). No new merge starts while a player view is open, and every merge's ffmpeg runs at low CPU priority — see "Merge hold while the player is open (#516)" below. Active merge can be cancelled (kills ffmpeg, cleans partial output).

## Merge scheduling (#410)

One merge cycle runs at a time, and a trigger that arrives while a cycle is running is **coalesced into a follow-up pass** rather than dropped. `mergeCompleted` sets `mergeRequested` and returns when `merging` is true; the running cycle then loops `mergeRequested = false` → `_mergeAll()` → repeat while the flag came back up. The flag is cleared *before* each pass, so a request that lands mid-pass survives into the next one, and every pass calls `getEpisodeGroups()` again — the group list is a snapshot of copies, so an episode that became `completed` mid-pass is only visible to a pass that re-reads it. Before this, a completion arriving during a pass was returned away and its episode stayed an unmerged `.mp4` + `.ass` pair until some later completion or a manual Merge. Both other callers go through the same door: the deferred-finalize hook (`finalizeDeferred()` on player close / boot, #63) and the Merge button.

A `failed` group is eligible again on the next pass (only `completed`, `merging` and `deferred` are skipped), so the retry bound is the number of requested reruns — one extra attempt per request, not a loop that runs until nothing is eligible.

Two cancel semantics, deliberately separate:

- **Global** (`cancelMerge()`, the Cancel button) sets `mergeCancelled`, which breaks the current pass and ends the cycle (it never kills a Shared Library export's merge, #576) — a pending requested rerun is dropped rather than resuming, which is what pressing Cancel is supposed to mean. The flag is raised whenever a cycle is running, not only when an ffmpeg command is live, so a Cancel during duration probing or between two groups is not lost. `_mergeAll` clears it on entry, so the next trigger or a manual Merge starts clean.
- **Per-translation** (`cancelMerge(translationId)`, reached from `cancelByEpisode`) joins a cancel set that lives for one merge cycle and kills ffmpeg only if that translation is the active merge. It never touches the global flag: doing so would break the whole pass and drop another episode's requested rerun. The pass consults the set live on every group (the snapshot's `mergeStatus` is frozen, so a cancel that lands mid-pass is invisible there), and the merge-failure path treats a set member the same as a global cancel — deleting the status instead of writing `failed`, which would otherwise be re-merged on the next pass. Entries are only added while a cycle is in flight and the set is cleared when the cycle ends.

`scanAndMerge` does not coalesce: it walks the directories and drives its own progress reporting, so queuing it behind a pass buys nothing. Called while a cycle is running it returns `{ merged: 0, failed: ['A merge is already running'] }` (same shape, no silent zero-merged success). An export merge doesn't set `merging`, so a scan started during one isn't refused: it waits for that file on the ffmpeg mutex (#576). It drains `mergeRequested` with a normal pass *after* its own `merging` flag is back down — otherwise `mergeCompleted`'s own busy check would swallow the request — and skips that drain when `mergeCancelled` is set, so a global Cancel during a scan cannot come back as a resumed auto-merge. The scan's own loop has no translation ids to match the cancel set against and does not check `mergeCancelled`, so cancelling mid-scan still only kills the current file and the scan continues to the next one.

## Verification and repair (Prepare for offline, #592)

`ensureFfmpeg` and `ensureFpcalc` only check that the files exist. Prepare for offline's binaries step ([Architecture › Prepare for offline](./architecture.md#prepare-for-offline-592)) checks that they run.

- **`verifyBinary(path, timeoutMs = 5000)`** (`ffmpeg-binaries.ts`) runs `<bin> -version` and resolves `{ ok: true, version }` with the first output line, or `{ ok: false, error }`; it never rejects. `checkFfmpeg()` in `index.ts` uses it for its own `-version` call.
- **Single-flight `ensure*`.** Each keeps a module-level in-flight promise: a call while an install runs gets that same promise, cleared when it settles. The boot install (`index.ts`, fire-and-forget) and the step can therefore never both download into the same directory and race on the `<name>.partial` rename (`lib/unzip.ts`). The `createBinaryInstalls` wrapper the boot task and the online kick-off share stays as it was.
- **`ffmpegStatus` replaces `ffmpegReady`.** The boot-time promise resolved once, so on a PC that booted offline auto-merge read `{ available: false }` until a restart, even after an install. `createFfmpegStatus(checkFfmpeg)` (`lib/ffmpeg-status.ts`) is a holder: `get()` is pending until the first `refresh()` (the boot install's, as before), then returns the latest check; `refresh()` re-runs `checkFfmpeg()` and replaces it. `createEpisodeCompletionHandlers` takes `getFfmpegInfo: () => ffmpegStatus.get()` and calls it at each of its three sites, and the export's `mergeExpected` awaits `ffmpegStatus.get()`. The binaries step ends with `ffmpegStatus.refresh()`.
- **Repair.** A binary that exists but fails `-version` is deleted and downloaded once more, then verified; a second failure is `failed` with the error, never a loop. After a delete of ffmpeg or ffprobe the step calls `clearFfmpegPaths()`, as `FFMPEG_DELETE` does, before the re-download, so nothing spawns a path that's gone. Offline, a failing binary is reported and left alone.
- **The repair gate.** Immediately before any delete (not once per step), and before *either* ffmpeg file is touched — `ensureFfmpeg` downloads both components again, so repairing ffprobe alone also replaces ffmpeg — the step asks who uses the binaries:
  - `downloadManager.ffmpegUser()`: `'merge'` while the ffmpeg mutex is held, a merge cycle runs or a command is active; `'task'` while the busy counter is up. `beginFfmpegTask()` returns an idempotent release, and the `DOWNLOAD_FIX_METADATA` and `DOWNLOAD_INJECT_CHAPTERS` handlers hold it for their whole body, since both spawn ffmpeg/ffprobe outside the queue. `isFfmpegBusy()` is `ffmpegUser() !== null`;
  - `playerPresenceService.isOpen()`: the player's remux, transcode and stream skip detection spawn all three;
  - `skipAnalysisService.getCurrentAnalysis() !== null`: it spawns fpcalc and ffmpeg.

  If any is busy, nothing is deleted or downloaded and the step reports a `warning`: "ffmpeg failed its check but is in use (a merge / the player / skip analysis). Close it, or wait for it to finish, and run Prepare for offline again." A delete that fails with `EBUSY` / `EPERM` / `EACCES` (Windows refusing a running `.exe` that started between the check and the delete) reports the same warning. `clearFfmpegPaths()` runs only once a file was actually removed, so a refused delete leaves the paths, and what `ffmpegStatus` reads, as they were.

## Merge hold while the player is open (#516)

A merge running under playback froze the player and made Windows report the app as "not responding": a `copy` merge streams several GB at full disk speed, usually on the disk the player reads from, and a re-encode takes every core from the player's own HEVC transcode. Merging is background work, so it gets out of the way. One code path on every OS:

- **Gate new starts.** `DownloadManager.setMergeHoldCheck()` (wired to `playerPresenceService.isOpen`, see `docs/player.md`) is consulted per group in `_mergeAll`, after the existing skip checks and the ffmpeg mutex's acquire and before the group is marked `'merging'`, and after the acquire for each file in `scanAndMerge`. A held group simply stays `pending`, so its source `.mp4` keeps serving `player:find-local-file`; no status and nothing persisted is new. A held `scanAndMerge` reports what it left in `failed` (`Merging is paused while the player is open: N files left`).
- **`heldRequest`, not `mergeRequested`.** A pass that stops at the gate sets `heldRequest` and ends the cycle. It must not leave `mergeRequested` up: the held pass breaks before any real await, so re-entering on it would spin main on microtasks — a real hang, the symptom being fixed. `mergeCompleted()` under the hold still resolves, either through a held pass or by recording `mergeRequested` for a running cycle, whose next pass then turns into `heldRequest`.
- **Re-check after the probe.** `runFfmpeg` awaits ffprobe with the group already `'merging'`; if the hold went up meanwhile it returns a held outcome without spawning, and `_mergeAll` puts the group back to `pending` (persisted), unlinks nothing, records no failure and fires no `mergeComplete`.
- **Release: `resumeHeldMerges()`** in `src/main/lib/episode-completion.ts`, on `playerPresenceService.onRelease`. It takes `heldRequest` (`takeHeldRequest()`), resolves ffmpeg/ffprobe and the codec fresh, and calls `mergeCompleted`. It deliberately skips the `autoMerge` check: a manual Merge / Scan & merge that stopped at the gate leaves the same request, and with auto-merge off it would be dropped. A stopped Scan & merge resumes as a queue pass only — files outside the download queue need Scan & merge clicked again. The player-lock release (`finalizeDeferredEpisodes`, #63) and this release can fire in either order; both end with the deferred episode merged exactly once. `onRelease` is a listener list (#574): boot registers `resumeHeldMerges` first, and a Shared Library export adds its own per-file hold listener for the length of a job (`docs/shared-library.md`), removing it through the returned unsubscribe. Each listener runs in its own `try`/`catch`, so one that throws is logged and the rest still run.
- **In-flight merges finish.** No SIGSTOP, no abort. Instead every merge's ffmpeg is lowered once, in the `'start'` handler, to `os.constants.priority.PRIORITY_LOW` (nice 19; `IDLE_PRIORITY_CLASS` on Windows) and never raised back — an unprivileged process cannot raise a child's priority on Linux or macOS. `'start'` is where fluent-ffmpeg has the PID. Errors (ESRCH, EACCES) are logged and never fail the merge. fluent-ffmpeg's `niceness` option is not used (skipped on Windows), and there is no `-threads` cap. CPU priority is not I/O priority, so a `copy` merge already running when the player opens still competes for the disk; that is bounded to one file.
- **Seam.** `setFfmpegDriver({ createCommand, probeDuration, setPriority, unlinkSync })` replaces fluent-ffmpeg, the probe, `os.setPriority` and the unlink `destroy()` uses on the killed merge's output, so tests run the real `runFfmpeg` body against a fake command and a fake Windows sharing violation.

## The ffmpeg mutex and export merges (#576)

`runFfmpeg` writes shared fields (`activeFfmpegCmd`, `activeMergeOutputPath`, `activeMergeTranslationId`), and the per-translation cancel, the global Cancel and `destroy()` all act on them, so two concurrent `runFfmpeg` calls would break all three. The `merging` flag can't guard a Shared Library export's merge: an export that set it would leave a queue trigger's `mergeRequested` with no cycle to drain it, and one that didn't would run beside `_mergeAll`.

- **`DownloadManager.ffmpegMutex`** (`src/main/lib/async-mutex.ts`, `createMutex()`) is FIFO: a release hands the lock straight to the first waiter, so a holder that releases and calls `acquire()` again in the same tick queues behind everyone already waiting. It owns the three fields plus `activeMergeOwner` (`'queue' | 'scan' | 'export' | null`).
- **Per merge, never per cycle.** `_mergeAll` keeps its snapshot skip checks before the lock, then acquires it per group. Everything from the source `existsSync` to the group's final status runs under one hold, in the old order: the file-lock deferral, the hold gate, `'merging'` and its persist, `runFfmpeg`, the unlinks and `completed` / `failed` / cancelled. Right after the acquire it re-checks what the wait may have changed (`mergeCancelled` or `destroyed` ends the pass, the cancel set skips the group), and a `finally` releases on every exit. The `mergeComplete` dispatch stays outside the lock. `merging`, `mergeRequested` coalescing and `mergeCompleted` are unchanged; a group waiting for the lock is still `'pending'`, on disk and in memory. `scanAndMerge` takes the lock per file, re-checking `destroyed` and the hold after the acquire. So a waiting export runs after at most the one queue merge or scan file holding the lock, however many triggers arrive, and a queue group waits for at most one export file.
- **`mergeForExport({ jobId, videoPath, subtitlePath, outputPath, codec, subMeta, onPercent, onWaiting, onAcquired, ffmpegPath, ffprobePath })`** is the export's door. It awaits the mutex (reporting `onWaiting` when it is held), then checks `destroyed` and the hold **before** `runFfmpeg`, so no ffprobe runs on the target while the player is open; `runFfmpeg`'s post-probe re-check still covers a player opened during the probe. It resolves `'done'`, `'held'` (nothing ran) or `'gone'` (the `.mp4` went while it waited, e.g. a Scan & merge took it). It never sets `merging` or `heldRequest`, never touches `mergeStatuses` or `queue.json`, never unlinks the sources, and leaves a failed output for the caller (S6b's run-time size rule needs its size). A quit rejects with `MergeQuitError`.
- **Cancel scoping.** The global `cancelMerge()` kills `activeFfmpegCmd` only when `activeMergeOwner !== 'export'`. The per-translation cancel was already safe, since an export leaves `activeMergeTranslationId` null. `cancelExportMerge(jobId)` kills only an `'export'` owner with that job id; one still waiting leaves the queue at once (an abortable `acquire(signal)`; the waiters behind it keep their order), so an export's Pause or Cancel doesn't wait for the merge in front of it, and one still probing stops before the spawn.
- **Hold and resume.** A `'held'` export never sets `heldRequest`, so `resumeHeldMerges` doesn't resume it: the export job waits on its own `playerPresenceService.onRelease` listener (a listener list since #574) and retries the same file. `resumeHeldMerges` stays registered beside it.
- **`destroy()` is unchanged.** Only one ffmpeg can run, so `activeFfmpegCmd` / `activeMergeOutputPath` is always the live one: for an export, the kill and unlink hit the export's ffmpeg and the target's `.anime-dl-tmp.mkv`. A queue group or scan file waiting on the mutex sees `destroyed` after the acquire and spawns nothing.

**Quit mid-merge.** `destroy()` sets `destroyed`, persists the queue, then sends `SIGKILL` to the active merge and unlinks its partial output (`runFfmpeg` records the output path beside `activeFfmpegCmd`, so scan outputs are covered too). On Windows `TerminateProcess` returns before ffmpeg's file handle is closed, so the first unlink fails with EBUSY every time and one about 5 ms later succeeds; the unlink therefore retries on EBUSY / EPERM, sleeping synchronously (`Atomics.wait`, 5 ms steps) for at most 200 ms, so quit stays synchronous. ENOENT counts as removed; any other error, or the deadline, logs a warning and leaves the `.mkv` to the boot fallback below. The `'start'` handler kills a merge that was still in its no-PID window. The kill must not undo the persisted queue: `_mergeAll`'s catch checks `destroyed` first and keeps the group `'merging'`, persists nothing and ends the pass; `scanAndMerge`'s catch stops without recording the file; both loops, the cycle's `while`, the scan drain, `mergeCompleted` and `scanAndMerge` themselves stop once `destroyed` is set. `runFfmpeg`'s `'end'` rejects when `destroyed` is set, because ffmpeg can exit 0 just before `destroy()` and deliver `'end'` after it — resolving there would unlink the sources of an output `destroy()` already removed.

**Boot fallback.** The merge start is persisted (`schedulePersist()` right after the `'merging'` set), so a crash, `kill -9` or power loss leaves `merging` in `queue.json`. `loadQueue` resets it to `pending` and, if the translation's `.mp4` still exists, first unlinks the matching `.mkv` (best-effort) — the truncated output a dead merge leaves at the final path. A merge that finished and already unlinked its `.mp4` is left alone. A partial Scan & merge `.mkv` has no merge status and is not covered (pre-existing).
