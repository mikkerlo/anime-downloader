# Built-in Video Player

In-app HTML5 video player with optional Anime4K WebGPU upscaling shaders. Uses `anime4k-webgpu` npm package for GPU-accelerated real-time upscaling.

## Custom Protocol

`anime-video://` protocol registered via `protocol.handle` serves local video files to the `<video>` element. The `stream: true` privilege enables HTTP range requests for seeking. The handler manually parses `Range` headers and returns 206 Partial Content responses using `fs.createReadStream({ start, end })` for proper seeking support. URL shape: `anime-video://{encodeURIComponent(filePath)}`. (MKV streaming does not use this protocol — it flows through MSE over IPC; see below.) The handler lives in `src/main/streaming/anime-video-protocol.ts` (`createAnimeVideoHandler`, deps-injected so it's unit-testable); `index.ts` registers it with a `DownloadManager.getActiveDownloadByPath` lookup.

## Watch While Downloading (#63)

A currently-downloading episode can be played from its growing `.part` file instead of re-streaming from the CDN:

- **Eligibility** (`player:find-local-file`): the translation's video item must be alive in the download queue with a known `totalBytes`, and the `.part` head must probe faststart (`probeMp4Faststart` — `moov` before `mdat`; a moov-at-end partial is unplayable). Otherwise the result is null and the caller falls back to CDN streaming. Resolution uses the queue item's own filename — during a download there is no `downloadedEpisodes` metadata to reconstruct the path from. Subtitles download before videos (queue priority) so the `.ass` is normally on disk when playback starts; if the player still beats it (Play in the first seconds after enqueue), `use-growing-file` polls `player:get-local-subtitles` (which maps `x.mp4.part` → sibling `x.ass`) every 3 s and hot-attaches the subtitle when it lands, giving up once the video download itself finishes or dies.
- **Serving**: the protocol handler advertises the download's expected final size in the `Content-Range` denominator (so duration/seek-range are correct up front) while the response's own `Content-Length` always matches the bytes actually delivered. Ranges extending past the current on-disk size are **tail-streamed**: read what exists, poll `fs.stat` (~200 ms) as the file grows, keep pushing until the promised range completes. The body errors if the backing download dies (failed/cancelled/vanished, or completed short of the promise).
- **Renderer** (`use-growing-file.ts`): the seek clamp derives from the element's `buffered` ranges plus a 2 s margin — with tail-streaming, `buffered.end` tracks the true time-domain download frontier. When that frontier is **unknown** — no element, or nothing buffered yet — the target passes through unclamped rather than being snapped back to the playhead (#237): clamping to an unknown bound turned every forward seek on a fresh `.part` into a no-op. An overshoot then stalls at the download frontier, and the "Waiting for download…" toast shows for as long as the playhead sits there — indefinitely if the download is paused or queued, since the tail stream counts those as growable; the clamp resumes on the next seek, because `frontier()` is re-read on every call, and there is deliberately no pull-back of an in-flight overshoot. Because a seek can now be issued for a position the element may never reach, the **OP/ED skip button no longer commits on the click** — it arms a pending landing and waits for the element's own `seeked`, committing only if the playhead arrived within `SKIP_LANDING_EPSILON_SEC` of the band end, and never hiding on click at all (#238). A short landing raises a "can't skip past the download" toast; a seek that never completes simply leaves the button up. Both toasts render into the same slot, so the short-landing one is gated — reactively, not just sampled when it fires — on `waitingToastVisible()` in `utils.ts`, the single predicate both `v-if`s read, and *retired* when that predicate rises rather than merely hidden — its 2.5 s timer would otherwise fade a stale notice back in on the next `playing`, since `waiting` normally fires ~2 s after a clamped landing. The MSE `mkvBuffering` / transcode notice renders into the same CSS class but stays outside the predicate: it is reachable only under `isMkv` (`.mkv`), which no `.part` path satisfies. The byte ratio from the downloads store is **display-only** (the `.seek-downloaded` fill): bytes are not time, a VBR byte-based clamp would overshoot. A dead download hands that slot back: the waiting toast yields to a banner, playback stays limited to the downloaded portion, and the short-landing toast is free to show — that being the one state where the skip genuinely can never land. The in-player **Watch Together** menu is disabled on a `.part` session (`SyncplayMenu :disabled="isPartial"`) because Syncplay assumes fixed file identity/size — but that is a UI gate on *starting* a session from the player, not on the feature: the connection lives in main and outlasts view mounts, so a room joined from the Watch Together sidebar stays connected, and a `.part` player mounted under it still pushes file and playstate normally. Nothing checks `isPartial` on that path.
- **Player lock / deferred finalize**: `PlayerView` reports its file via `player:opened` / `player:closed` (plus webContents-destroyed cleanup) into `src/main/services/player-lock/`. While locked, download completion skips the `.part` → final rename (EPERM on Windows; 404s the player's URL everywhere) and marks the episode `'deferred'` in the persisted merge-status map. On lock release — and at boot, for crash recovery — `finalizeDeferred()` renames and re-runs the episode-complete tail (auto-merge, cold move, skip analysis). The lock is **two-way**: `player:find-local-file` returns null for a translation whose merge status is `'merging'` (the final-path `.mkv` is half-written and the source `.mp4` is about to be unlinked — the caller falls back to CDN streaming), and `_mergeAll` re-defers any group whose video file the player grabbed between finalize and the merge pass.

## Video Playback

- **Local .mp4**: Served via `anime-video://` protocol
- **Local .mkv**: Progressive playback via **MSE (MediaSource Extensions)**. The main process ffprobes the MKV for duration and codec parameters (H.264 → `avc1.…`, HEVC Main / Main 10 / Main Still Picture → `hvc1.…`, plus AAC → `mp4a.40.2/.5/.29`), then spawns ffmpeg with `-c copy -movflags +frag_keyframe+empty_moov+default_base_moof -f mp4 pipe:1` and streams its stdout to the renderer via `player:stream-chunk` events. For HEVC, `-tag:v hvc1` is added so the fMP4 track carries parameter sets in the sample entry (Chromium's MSE rejects `hev1` tags). `player:remux-mkv-stream` returns an `MseOpenResult` — `{ sessionId, generation, duration, mimeType, hasSubtitlesPending, contentStart, refusedSeek }` — immediately. That shape is declared once, ambiently, in `src/shared/types/player.d.ts` (#294); main and preload reference it by name rather than restating it, and the renderer inherits it through the `window.api` signature without naming it. The renderer creates a `MediaSource`, sets `duration` upfront, calls `addSourceBuffer(mimeType)`, appends each incoming chunk, and binds `<video>` to the `URL.createObjectURL(mediaSource)`. Backpressure: main tracks pending-bytes per session, pauses `ffmpeg.stdout` when pending data exceeds 64 MB, and resumes once it drains below 16 MB; renderer acks via `player:stream-ack` each 1 MB appended. Subtitle extraction runs in parallel and is pushed via `player:stream-subtitles` when ready. SourceBuffer quota is managed by evicting buffered data >60 s behind the playhead on every `updateend`, with a `QuotaExceededError` retry path. `player:cleanup-remux` SIGKILLs active ffmpeg processes and sweeps the temp dir (`os.tmpdir()/anime-dl-remux/`, used for temporary remuxed `.mp4` files and extracted subtitle files such as `.ass`).

  **Session lifetime and the reaping rule** (#280): `player:cleanup-remux` is the **only** reaper. `player:closed` merely releases the download lock (`playerLockService.close`), `cleanupAllSessions` has no production caller, `onBeforeQuit` never touches streaming, and there is no idle sweep — so a session that nobody cleans up survives until the next `.mkv` open, whose `player:cleanup-remux` kills *every* registered session unconditionally. `player:close-stream-session` (#291) is the one *targeted* reaper alongside it — see the supersede bullet below. Four consequences the code depends on:
  - **The renderer must issue the cleanup itself, synchronously at teardown.** `PlayerView`'s `onBeforeUnmount` does, gated on `remuxedPath || hadActiveStream || mkvPreparesInFlight > 0` — the third term covers the window where main has already registered and spawned a session but the reply that assigns `streamSessionId` has not landed. It is a **count, not a boolean**: nothing serialises `prepareMkvForPlayback`'s three call sites and the MSE open sits behind no blocking overlay, so a second open started while the first is parked in `probeMkvForMse` would otherwise clear the flag out from under it in its own `finally`. It has to stay synchronous: a blanket kill issued after an `await` can outlive the close and SIGKILL a *successor* `PlayerView`'s session. The same reasoning is why the blanket `playerCleanupRemux()` calls **inside** `selectTranslation` / `goToEpisode` are `unmounted`-guarded after their preceding await: `resetMseState()` clears `streamSessionId` at unmount but nothing clears `remuxedPath`, so on the legacy-remux population those guard conditions still read true on a dead instance.
  - **The two stream handlers self-reap if a cleanup overtook them.** `player:remux-mkv-stream` and `player:remux-mkv-stream-transcode` capture a module-local `cleanupGeneration` at handler entry and, immediately after `registerSession` and *before* `spawnFfmpegForSession`, call `cleanupSession(sessionId)` and return `{ error: 'cancelled' }` if it moved. That closes the race where the teardown cleanup arrives while main is still inside `probeMkvForMse`: the sweep finds nothing, the registration lands behind it. The check sits above the spawn on purpose — at that point the `return` is what makes the ffmpeg process never exist, rather than buying a spawn-then-kill. Both handlers **re-read the generation once more immediately before the reply**, because the window reopens below the first check: the `Ffmpeg.ffprobe` subtitle probe and the `await offsetPromise` / `await anchorPromise` content-start probe are two further suspension points, and a cleanup landing in either one does sweep the session — but without the second read the handler still returned a full success payload naming a dead, deregistered `sessionId`. With it the invariant is not merely "no ffmpeg is spawned behind a sweep" but **no reply ever describes a swept session**. The renderer treats `{ error: 'cancelled' }` as an unwind, never as an open failure: falling through to the legacy full-file remux — the one spawn nothing can kill — is the worst available response to "a cleanup overtook your open". Both renderer paths surface it as `stream cancelled` rather than the bare string, since every caller assigns the error straight to `remuxError.value`. On the copy path (`prepareMkvForPlayback`) that arm is load-bearing — it is what prevents the legacy fall-through; on the transcode path (`prepareHevcTranscode`) there is nothing below the arm to fall into, so the rename is purely about what the user is shown.
  - **Two ffmpegs run outside the session map entirely, so they are uninterruptible once issued.** The first is `player:remux-mkv` (the legacy full-file remux), which the renderer must not issue on a dead component. The second is **`extractFirstSubtitle`** (`player.ipc.ts`), the parallel subtitle extraction both stream handlers and the legacy handler kick off: a second fluent-ffmpeg spawn, also unregistered, writing an `.ass` into the same `streamingService.tmpDir` that `player:cleanup-remux` deletes. It survives a close exactly like `player:remux-mkv` does, and unlike it, it is issued by the very handlers this paragraph is about. Only the **pre-spawn** generation check skips it (its `return` sits above the extraction); a cleanup arriving any later — including one the reply-time re-read catches — does not, because the extractor has already been kicked off by then, and it goes on writing into a directory that has been swept. Neither spawn calls `registerSession`, so `playerCleanupRemux` cannot reach either — not at unmount, not on the next open, not ever. The legacy remux in particular runs to completion writing an `.mp4` that a later sweep `unlinkSync`s out from under it, and still returns that now-deleted path as success. The `unmounted` checkpoint above `runLegacyRemuxIpc` in `prepareMkvForPlayback` is the only guard it can have; the same is true of the transcode spawn, whose cleanup bump always *precedes* its handler entry so the generation check can never fire for it. `cleanupSession` unlinks `${baseName}-${sessionId}.ass` (derived from the session's own `mkvPath`, so no call site grows a parameter; `fs.unlinkSync` in a `try`, because making `cleanupSession` `async` would silently un-await the blanket sweep and let `rmdirSync(tmpDir)` race the unlinks that must precede it) so the targeted close is self-contained — but that reaps the **artifact**, not the **extractor**. `extractFirstSubtitle` may still be writing and can recreate the file after the unlink; the residual is a stray `.ass` the next blanket sweep removes. Bringing the extractor into the session map, or giving it a cancellation token, is tracked separately.
  - **Two opens can be in flight at once on a LIVE component, and the loser is reaped by the renderer** (#291). Nothing serialises `prepareMkvForPlayback`'s three call sites and the MSE open sits behind no blocking overlay, so while one open is parked in main's `probeMkvForMse` — *above* `registerSession`, so main's map is still empty — the user can pick another translation. Neither caller-side `if (remuxedPath.value || streamSessionId.value)` fires (both terms are written only *after* an open replies), so no `player:cleanup-remux` is issued, no generation moves, and **both** handlers register and spawn. Whichever reply lands second wins `startMseSession`, which does no teardown of a prior session; the loser's ffmpeg is orphaned in main with nobody holding its id. Main registering two sessions here is correct — the fix is renderer-side: `PlayerView` keeps a **component-scope** `prepareEpoch` (a per-instance top-level `let`; module scope would make two live `PlayerView`s supersede each other), each `prepareMkvForPlayback` takes `const myPrepare = ++prepareEpoch`, `prepareHevcTranscode` receives it as a *parameter* (it is a continuation of the same prepare, not a new one), and the `unmounted` checkpoint ladder above is generalised to one `shouldBail(myPrepare)` predicate meaning "unmounted **or** superseded". A superseded checkpoint closes the session **its own** open returned, via `player:close-stream-session` — never `playerCleanupRemux()`, which would SIGKILL the winner's session and unlink the shared tmpDir. Four properties that ladder has to have: the supersede bail sits **above** the two blanket `playerCleanupRemux()` calls that are already *inside* those functions (the `!mseOk` branches — the failure mode most likely to be missed, since they are not on the "unwind path" as such); no checkpoint is ever placed between issuing an open and awaiting it, so the rule is always "await the open you issued and close whatever id comes back"; the close is issued **fire-and-forget** (`void … .catch(() => {})`), because an awaited close inside a bail block would become the preceding suspension point for every checkpoint below it; and the unwind **mutates no other shared renderer state** — in particular it does not clear `mkvBuffering` (unreachable for a loser: no `await` separates the checkpoint above it from the assignment) or `transcodingHevc` (already cleared by the superseder's own `resetMseState()`, and clearing it on the unwind would drop the **winner's** live transcode overlay). The three callers route the unwind through `reportPrepareError`, which drops `PLAYER_CLOSED_BAIL` rather than painting `player closed` into `remuxError` on a live component. Property (4) has a **caller-side** half as well: `selectTranslation`'s and `goToEpisode`'s `!prep.ok` arms also release their own flow's flag (`switchingTranslation` / `navigating`), and on a supersede that arm runs on a live component where a newer run of the same flow may already own the flag. The guard there is an **ownership compare** (`translationEpoch` / `navigationEpoch`, each taken where the flag is set), *not* `prep !== PLAYER_CLOSED_BAIL`: that test says only *that* this run was superseded, never *by whom*. The two flows supersede each other freely and neither touches the other's flag, so skipping the clear on every superseded unwind would strand it for the life of the component — `navigating` stuck true disables prev/next and makes every later `goToEpisode` a no-op at its own re-entrancy guard, and `switchingTranslation` stuck true leaves `TranslationMenu`'s button on `pointer-events: none`. Because the loser therefore *does* release `navigating` when it still owns it, the syncplay multi-step walk in `handleRemoteEpisodeChange` carries its own stop term alongside `!navigating.value`: without it the loop reads the released flag as permission to take another step, that step supersedes the user's translation switch in turn, and the pick is dropped silently. An explicit pick outranks the room's episode walk. That term reads the **monotonic** `translationEpoch`, sampled once into a `walkTranslation` const before the walk (`translationEpoch === walkTranslation`), not the transient `switchingTranslation` flag: the flag is only up while a switch is *in flight*, and a pick that takes the stream fall-back is a single `playerGetStreamUrl` round trip that clears it in its own `nextTick` — comfortably before a step parked on an MSE open resumes, after which the loop re-reads both flags as false and steps anyway. A sampled epoch cannot be un-set. It also settles the **entry** case deliberately rather than by accident of which flag happened to be up: a switch already in flight when the room's episode change arrives no longer suppresses the walk outright (the sample is taken *after* that pick's bump), so the walk starts and stops at the first pick made **after** it began — a pick that predates the walk is not a response to it, and suppressing the walk on one left the user toasted about a room move the player never followed. **The targeted close is not a new source of deregistration-under-a-parked-handler**: the renderer only learns a `sessionId` from an open's *reply*, so by the time it can name a session that session's handler has already returned. The complete set of things that can deregister a session while its own open handler is still parked is therefore unchanged — the blanket sweep, which bumps `cleanupGeneration` before sweeping — and the generation compare at all four reply-time checkpoints stays a *complete* detector. `player:close-stream-session` deliberately does **not** bump. There is no main-side per-sender eviction in `registerSession`, on purpose: it would add a second supersede authority (per-`webContents`, decided at registration time) racing the renderer's (per-prepare, decided at the reply), and having the eviction bump the generation is not even available — `openedAtGeneration` is captured at handler *entry* and the next read is immediately under `registerSession`, so the evicting open would cancel *itself*, leaving zero sessions and an error banner where the user expected video.

  **Frame-accurate seeking** (#198): ffmpeg's fmp4 muxer always normalizes its output PTS to start at 0 per session (`tfdt.baseMediaDecodeTime` is written relative to track start, not absolute file PTS, even with `-copyts`), so the renderer must offset the buffer by the run's true content start to map fragments onto the absolute file timeline. Both open (`MseOpenResult.contentStart`) and mid-stream seek (`player:stream-seek` → `timestampOffset`) hand that value back; the renderer sets `sourceBuffer.timestampOffset` to it and keeps `<video>.currentTime` on the user's exact target.

  The content start is **path-specific and must be measured, not guessed**:
  - **Stream copy** can only start at an indexed keyframe, and ffmpeg's `-ss` input seek uses the container's *sparse* seek index — on Matroska it lands on the keyframe *strictly before* the requested time (a ~0.5–1 s deadzone after each keyframe still snaps to the previous one). A frame scan sees *every* keyframe, so a pre-snapped `-ss <keyframe>` **double-snaps ~one GOP early** while the renderer labels the buffer with the un-snapped time — the buffer ends up shifted by a GOP and subtitles run seconds ahead. The fix: pass the **raw** requested time as `-ss` (no pre-snap) and measure the run's true `timestampOffset` with `probeCopyTimestampOffset` — two concurrent `ffmpeg | ffprobe` pipe pairs (nothing touches disk): one replicates the input seek with `-copyts` into NUT (the only pipeable container that preserves absolute timestamps) and reads the landing keyframe's **absolute PTS**; the other replicates the live fMP4 mux verbatim and reads the **output PTS** that keyframe is emitted at (B-frame reorder over the `-avoid_negative_ts make_zero` anchor, which zeroes on the earliest DTS across *both* streams — so the keyframe's PTS alone would be off by a sub-second margin). `timestampOffset` = absolute − emitted. The probes run concurrently with the session spawn (their result feeds only the IPC reply), so they never delay first bytes.
  - **Transcode with copied audio** (AAC source, the common case): accurate-seek trims the *decoded* video to the exact `-ss` time, but a stream-copied track can't be trimmed — the audio starts at the seek's keyframe cluster (up to one GOP before the target) and `-avoid_negative_ts make_zero` anchors the whole output timeline on it. Labeling with the raw request would leave every sample ~one GOP late (the #198 desync, transcode edition), so the anchor is the copied audio track's absolute landing, probed in the **same muxed demux context** as the live run (a lone `-map 0:a:0` input seek positions differently than one with the video stream mapped).
  - **Full transcode** (video + audio both re-encoded) trims every stream to the exact `-ss` time, so the content start *is* the raw request — no probe.

  **The open position must be inside the file, and is rejected — never clamped — when it is not** (#275). `boundInitialSeek(initialSeek, probe.duration, sessionId)` in `player.ipc.ts` folds the long-standing non-finite / `<= 0` normalisation together with `requested >= duration → 0`, and both open handlers call it **below** the pre-spawn self-reap (so a cancelled open never spends a `console.warn` on a seek it will not use) and **above** the offset probe and the spawn (so `probeCopyTimestampOffset` / `probeSeekAnchor` and ffmpeg read one value by construction — bounding inside `spawnFfmpegForSession` would recreate the #198 desync and hide the bound from the test seam). `probe.duration` needs no validity check there: `probeMkvForMse` returns `null` unless it is finite and `> 0`, and both handlers bail on that first.

  Rejecting rather than clamping is the whole point. An out-of-range `-ss` does **not** produce an empty run: ffmpeg's Matroska demuxer clamps the input seek to the last keyframe and emits the final GOP, so `-ss duration`, `-ss 3000` and `-ss 999999` are byte-identical runs. The session opens parked at the last frame, `ended` fires, and `onVideoEnded` auto-advances to the next episode — the user picks episode 7 and lands on episode 8. Clamping the request to `duration` is therefore provably clamping it to 999999, and no fixed pre-roll margin works either: the window a margin must clear is the release's final GOP, measured from 0.645 s (h264, 2.002 s keyint) to 10.428 s (hevc, x265 default `keyint=250`), so `duration - 1` lands *inside* the final-GOP window on one release and *before* the buffer start on another. A position that is not inside the file is a stale record, not a seek; there is nowhere correct to land, so the open starts at 0. `resolveMkvSpawnTarget` already states the same rule with its `< 0.95` gate — this applies it against the authoritative duration instead of the record's own.

  **The renderer drops its resume land on main's decision, not on a re-derivation of it** (#295). `boundInitialSeek` returns `{ seek, refused }` — `refused` set by the same `requested >= duration` expression that takes the branch — and both open handlers put it on the reply as `MseOpenResult.refusedSeek`. `startMseSession` takes that boolean and zeroes the resume land when it is set; there is no duration comparison on the renderer side at all. Bounding only main leaves the symptom — main opens at 0, the renderer still lands on a target past the end, Chromium clamps that write to the seekable end, `ended` fires. Transporting the decision rather than its inputs is what keeps the two sides in agreement by construction instead of by test: a target in `[duration, duration + 1)` still has main spawn (`initialSeek = resumeTarget - 1` is inside the file) and the renderer still land, deliberately — a position within one pre-roll of the end *is* the end — but that now follows from there being one rule, not from two copies matching. It is also why the flag is a boolean and not the bounded seek: `seek === 0` is ambiguous between the refusal and the non-finite / `<= 0` normalisation, and a third zeroing path added later (the growing-`.part` exemption below is the obvious candidate) would be silently reclassified as a refusal. `refusedSeek` is required on the reply (main always knows) and optional on `StartMseSessionOpts`, fail-open: an omitted value leaves the land untouched.

  **The bound must not reach a growing/partial file.** `prepareMkvForPlayback` is gated on `isMkv`, which requires a `.mkv` extension, and a growing partial is `<name>.mkv.part` — so the probe duration here is always a finished file's. If a growing-MKV playback path is ever added it must not inherit this bound against a partial duration, which would refuse every legitimate resume past the current tail.

  **`player:stream-seek` is deliberately exempt.** Its target is already bounded by the element (`resolveSeekTarget` in `PlayerView.seek`, `v.currentTime` in `handleUnbufferedSeek`), and a user scrub to the last seconds landing in the final GOP is *correct* — applying the open's rejection there would throw a user who scrubbed to 23:00 back to the start.

  `probeSeekAnchor(session, time)` encapsulates that policy (`seekAnchorStreamFor`: copy → video, transcode+audio-copy → audio, full transcode → none) and is what both open handlers and `player:stream-seek` call — always concurrently with the session spawn.

  Either way the buffer starts at a real keyframe (SAP) and is correctly labeled, so `<video>.currentTime` stays on the user's target: Chromium decodes from the leading keyframe and presents the target frame in sync — the standard in-buffer seek. For an unbuffered (skip) seek, `handleUnbufferedSeek` sends the raw target to `player:stream-seek` and, after setting the returned `timestampOffset`, leaves the playhead where the user put it. For resume-from-middle the composable lands `currentTime` on the saved position once the first fragment arrives (moving it off 0, which Chromium won't auto-jump), so `PlayerView.resumeFromSavedPosition` does *not* also seek. Play-from-start is untouched. Enable **Settings → Debug → Player seek diagnostics** (`playerDiagLogging`, applies live) or set `ANIME_DL_PLAYER_DIAG=1` to log the exact ffmpeg args and each probed landing vs the requested time — to the main-process console and to `userData/player-diag.log` (openable from the Debug tab), so packaged builds can retrieve it.

  **Seek commit + post-respawn buffer gate** (#127): the scrubber commits the seek to `<video>.currentTime` only on release (`@change`), not on every `@input` drag tick — each `currentTime` write fires a `seeking` event, and committing per-tick churns the MSE pipeline (an ffmpeg respawn per debounce window plus repeated SourceBuffer parser resets), which on Linux/WSL produces repeated `readyState=1` stalls and audio dropout. During the drag only the displayed time + tooltip update. After any unbuffered-seek respawn, `use-mse-player` pauses playback behind a buffer-ahead gate (`mkvBuffering` + `waitForBufferAhead`) until a margin of fresh data is buffered ahead, then resumes — 3 s / 15 s on the transcode path (ffmpeg runs at ~real-time with little headroom), 1.5 s / 5 s on the stream-copy path (fills far faster, but still needs the decoder to bed in before the element renders, or the same WSL stutter recurs).

  **HEVC transcode fallback**: When `MediaSource.isTypeSupported` returns false for an `hvc1`/`hev1` mime (typical on Linux Electron builds, WSL2, and any machine without a platform HEVC decoder), the renderer branches to `player:remux-mkv-stream-transcode`. This path reuses the same session/backpressure/generation-counter plumbing but replaces `-c copy` with a real-time H.264 encode. Encoder selection is performed on demand the first time this path is used via `pickH264Encoder()`, which then caches the first successful result for subsequent transcode sessions. The probe order is `h264_vaapi` (Linux, trying each available `/dev/dri/renderD*` render node), `h264_nvenc`, `h264_qsv`, and `libx264`, using a 1-frame `testsrc` dry-run encode; the first one to succeed is cached. Audio is stream-copied when the source is AAC, otherwise transcoded to AAC 192 kbps. The resulting mime is `video/mp4; codecs="avc1.640028, mp4a.40.2"`. Consent UX is controlled by the `hevcTranscodeOnPlay` setting (`ask` | `always` | `never`): in `ask` mode the renderer shows a modal with four choices — Transcode once, Always transcode (persists the setting to `always`), Open in external player (uses `shell:open-external-file` → `shell.openPath`), or Cancel. Legacy `player:remux-mkv` is still used as a fallback for other non-MSE-compatible codec combinations. To keep IPC traffic under control when the encoder runs at 30×+ realtime, the main process coalesces ffmpeg stdout into ~256 KB batches before sending `player:stream-chunk` events; without batching the renderer main thread sees 200+ IPC events per second and the video compositor starves. **Known limitation**: on systems with a weak Chromium video render path (notably WSL2), even the transcoded H.264 stream can exhibit picture-lag during steady-state playback where audio and subtitles advance at 1× but displayed frames fall progressively behind. The "Open in external player" modal option is the workaround on affected systems.
- **Non-downloaded episodes**: Streams directly from smotret-anime CDN via `player:get-stream-url` IPC

## Anime4K WebGPU Pipeline

When shaders are enabled and WebGPU is available:
1. Video frames copied to GPU texture via `device.queue.copyExternalImageToTexture()`
2. Anime4K preset pipeline processes the texture (compute shaders)
3. Output rendered to canvas via fullscreen quad render pass
4. Frame loop driven by `video.requestVideoFrameCallback()`

Preset modes: Mode A (1080p source), Mode B (720p source), Mode C (480p source). Falls back to plain `<video>` when WebGPU is unavailable.

## Subtitles

ASS subtitles are rendered natively using [JASSUB](https://github.com/ThaUnknown/jassub) (libass compiled to WASM), preserving full ASS styling — colors, positioning, fonts, effects, and sign translations. JASSUB renders subtitles onto a transparent canvas overlaid on the video element.

- **Local files**: `player:get-local-subtitles` reads raw `.ass` file alongside the `.mp4`
- **Streaming**: `player:get-stream-url` fetches raw ASS content from smotret-anime API
- Raw ASS content is passed to the renderer and fed directly to JASSUB via `subContent` option
- JASSUB worker is bundled by Vite via `?worker&url` import; at runtime, the worker code is fetched, `import.meta.url` references are replaced with concrete URLs, and a blob URL is created for classic worker compatibility (Electron doesn't support module workers with `file://` protocol). A Vite plugin (`jassub-electron-fix`) strips `type: "module"` from JASSUB's Worker constructor.
- On subtitle update (e.g., translation switch), the previous JASSUB instance is destroyed and a new one created

## Quality Selector

Dropdown in player controls showing all available stream heights (e.g., 1080p, 720p, 480p). Available streams are returned by `player:get-stream-url` IPC. On quality switch: updates `<video>` src, preserves playback position. Only visible when streaming (not for local files).

## Translation Selector

Dropdown in player controls showing all available translations for the current episode. Translations are passed from `AnimeDetailView.episodeRows` data through `App.vue` to `PlayerView` as `{ id, label, type, height }[]`. Each option shows the author name and a sub-label with type (RU SUB, EN DUB, etc.) and quality. On switch: calls `player:get-stream-url` with the new translation ID to get a fresh stream URL + subtitles, updates `<video>` src and subtitle track, preserves playback position. Only visible when streaming with more than one translation available.

## Episode Navigation

Prev/next episode buttons in the title bar for seamless binge-watching. `AnimeDetailView` passes the full `filteredEpisodes` list (all episodes, not just the current page) as `allEpisodes` prop through `App.vue` to `PlayerView`. Each entry contains `{ episodeInt, episodeFull, translations, downloadedTrIds }`.

Translation resolution for the target episode: (1) prefer any downloaded translation (downloaded wins over streaming — same ID first, then same type, then any downloaded), (2) same translationId via streaming, (3) best quality of same type via streaming, (4) first available. Cleans up previous MKV remux when switching.

Auto-advance: when video ends and next episode is available, shows a 5-second countdown overlay. User can cancel or let it auto-navigate to the next episode.

Configurable keyboard shortcuts: `playerPrevEpisode` (default Shift+ArrowLeft) and `playerNextEpisode` (default Shift+ArrowRight) in Settings > Shortcuts.

## Pre-fetch Next Episode

While the user watches episode N, `PlayerView` opportunistically enqueues a download for episode N+1 to make the next transition instant. Trigger is configurable via `prefetchNextEpisode` (Settings > Player): `off`, `open` (fires from `onDurationChange`), `time-5min` (fires from the same `cumulativePlayTime` accumulator that powers watched-flag detection — counts real playback only, not wall clock), or `progress-50` (default; fires from `onTimeUpdate` when `currentTime / duration >= 0.5`). Each episode fires at most once via a `${animeId}:${nextEpisodeInt}` key set, so seeking back and forward across the threshold doesn't re-enqueue. Translation matching prefers an exact `(type, author-label)` match on the next episode's translation list, falling back to best quality of the same type. The pre-fetch routes through the existing `download:enqueue` IPC — no new channels — and is silently skipped when the next episode is already on disk (`downloadedEpisodesGet`), already in the live queue (any non-terminal status), or — for auto-download-subscribed shows — strictly newer than the subscription's frozen `initialEpisodesAired` snapshot. The auto-downloader sets `initialEpisodesAired` to `episodes_aired` at subscribe time and never advances it, so the boundary represents "what the auto-downloader is responsible for." Older episodes — both pre-subscription backlog and any already-aired episode the user later deleted — still pre-fetch from the player. A small "Pre-fetching episode N…" toast appears for ~2.5s when an enqueue actually fires; the persistent `↓ Ep N · X% · Y MB/s` chip in the title bar tracks progress thereafter via 1s polling of `download:get-queue`. To avoid disk I/O contention with ffmpeg's source reads (which causes visible stutter on unbuffered seeks when both share a drive), the player auto-pauses the in-flight pre-fetch on `seeking` events that would trigger an ffmpeg respawn — i.e. MSE playback with the seek target outside the SourceBuffer's `buffered` ranges. In-buffer seeks (pure SourceBuffer scrubs) and non-MSE playback skip the pause entirely since they don't read from the disk we're writing to. The pause resumes 1.5s after the last `seeked` event (debounced so a burst of seeks coalesces into one pause/resume). On player close mid-debounce the resume is fired explicitly so the queue keeps draining. A small `↓ Ep N · X% · Y MB/s` indicator appears in the player title bar while a pre-fetch is in flight; status is polled via `download:get-queue` on a 1s interval to avoid clobbering AnimeDetailView's `download:progress` listener (which `removeAllListeners` would tear down). Once enqueued the download is not aborted on player close — symmetric with manual downloads.

## Overlay Stacking Order (#220)

Everything the player draws lives inside `.player-overlay` (`position: fixed; inset: 0; z-index: 1000`), which is the stacking context the whole scale below is scoped to. Pick a layer from this table when adding an overlay — the numbers are a deliberate order, not free-floating magic values, and `test/renderer/player-overlay-stacking.test.ts` pins the relationships that matter.

| Layer | Element | Anchor |
|---|---|---|
| `20` | `.remux-overlay` — blocking modal | full-screen |
| `15` | `.auto-advance-overlay` — next-episode countdown | centered |
| `13` | `.controls-bar` | bottom |
| `12` | `.skip-button-overlay` — Skip OP / Skip ED | bottom-right |
| `10` | toasts: `.streaming-banner`, `.resume-toast`, `.stream-skip-toast`, `.prefetch-toast`, `.syncplay-toast`, `.mkv-buffering-toast`, `.syncplay-paused-by` | all top |
| `5` | `.title-bar` (`player/PlayerTitleBar.vue`) | top |
| `1` | libass subtitle canvas (`.libassjs-canvas-parent`, inside `.video-wrapper`) | full-screen |

Two rules the table encodes:

- **The controls bar outranks the skip button.** `.controls-bar` has `position` + `z-index`, so it forms a stacking context, and the four dropdowns that pop upward out of it — Anime4K, Sync, Translation, Quality, all `.preset-menu` from `assets/player-menus.css` — are confined to *its* level however they are styled. A `z-index` in `player-menus.css` therefore cannot lift a menu above anything outside the bar; the bar is the only lever. Before #220 the bar sat at `5` and the skip pill covered the open menus and stole clicks meant for them.
- **The bar wins its overlap, so bottom-anchored overlays must clear its box.** The bar is 130px tall (40 top padding + 16px `.seek-container` + 16px margin + 38px `.controls-row`, whose tallest child is the `.ctrl-btn.big` play button, + 20 bottom padding) and carries `@click.stop` with no `pointer-events: none`, while its gradient is nearly transparent at the top. Any bottom-anchored element inside 130px is an invisible dead zone, which is why `.skip-button-overlay` sits at `bottom: 145px`. It and `.controls-bar` are the file's only literal `bottom:` declarations; `.remux-overlay` and `.auto-advance-overlay` also reach the bottom edge, via `inset: 0`, but both outrank the bar. A future bottom-anchored toast needs a layer above `13` *and* the same clearance — and grepping for `bottom:` alone will not find the `inset` form.

`.seek-knob` (`2`) and `.seek-band` (`1`) are *not* on this scale: they resolve inside the controls bar's own stacking context, so they are not comparable with the libass layer's `1` despite the matching number. Conflating those two contexts is what produced #220.
