# Watch Together (Syncplay)

Two (or more) users watching the same anime together over the Internet, staying in lockstep on playback position. Compatible with the [Syncplay](https://syncplay.pl) protocol — connects to community servers (`syncplay.pl:8999` default) and interoperates with the reference `syncplay.pl` desktop client (mpv/VLC), so a friend can watch along from any player Syncplay supports.

## Module: `src/main/syncplay.ts`

Standalone TCP/TLS client. **TLS-only:** `net.Socket` opens the TCP connection, the very first message we send is the Syncplay TLS probe `{TLS:{startTLS:'send'}}` (the key must be `startTLS` — servers close the socket immediately on anything else), and only after the server replies `{TLS:{startTLS:'true'}}` and `tls.connect({ socket })` finishes its handshake (with `rejectUnauthorized` left at its default `true`) do we send the `Hello` message containing username/password. The server password travels as an **MD5 hex digest** (`md5Hex()` in the module) — Syncplay servers MD5 their own `--password` at startup and compare digests, so sending it plaintext is always rejected with "Wrong password supplied"; MD5 is the protocol's wire format, not a security claim, since the session is already inside TLS. Servers that do not support STARTTLS — or whose certificate fails verification against `host` — drop the connection with a clear error. Line-delimited JSON (each message is one JSON object followed by `\r\n`). All protocol-level concerns live here — the renderer only emits high-level playback events.

State machine: `idle → connecting → tls-probing → tls-handshake → hello-sent → ready → (reconnecting) → disconnected`. On transport error: exponential backoff reconnect, max 5 attempts. On protocol error (wrong password, bad handshake, server refused TLS, protocol garbage): abort without retry — a non-Syncplay server will not become one on retry. The handshake watchdog (#215) is explicitly *not* in that list: 8 s of pre-`ready` silence (strictly below the Settings test button's 10 s renderer timer, so the informative message always wins the race; also always ahead of the OS SYN timeout, deliberately superseding `connect ETIMEDOUT`) records a neutral, phase-naming detail ("No reply received in 8s while in `tls-probing`"; in `connecting`, where nothing has been sent yet, "Could not establish a TCP connection within 8s — the host may be unreachable or the port filtered"), emits it as a `warn` room-event, and destroys the socket — the normal `close` → reconnect path then runs, because a transient hang is exactly what auto-reconnect exists for. For a watchdog-fired attempt, `onSocketError()` suppresses both the fatal-TLS `ECONNRESET` classifier (destroy-before-`secureConnect` manufactures that precise signature) and the fall-through `Connection error` room-event, so the app's own destroy is never reported as the server's fault. Garbage detection (#215) is pre-`ready` only: 5 JSON parse failures in one attempt, or 64 KB received without a single valid message (`GARBAGE_PARSE_FAILURE_LIMIT`/`GARBAGE_BYTE_CAP`), abort with "Server sent data that is not Syncplay protocol — is this a Syncplay server?"; post-`ready` a corrupt line keeps the skip-and-log behavior so a live session doesn't die on one bad frame. The counters deliberately survive the TLS upgrade — plaintext-phase garbage counts toward the same attempt's verdict.

**Per-socket vs per-session state:** `resetTransportState()` clears everything that belongs to one socket — `rxBuffer`, `tlsUpgraded`, the `ignoringOnTheFly` counters, `serverRtt`, the garbage-detection counters and the watchdog *timer* (#215) — and is called both by `tearDown()` and by the reconnect path in `onSocketClose()`. The watchdog's `watchdogDetail`/fired flag are deliberately **not** in this list: `onSocketClose()` calls `resetTransportState()` before it composes the disconnect reason, so a detail parked here would be erased on every path that could read it — they reset per attempt in `openSocket()` with the other detail slots instead. The reconnect path deliberately does *not* go through `tearDown()`, so it must reset this itself: a stale `tlsUpgraded` makes `handleTls()` treat the retry's probe reply as a spurious post-upgrade message, `tls.connect()` is never called again, and the client hangs in `tls-probing` until the server times it out (#216). Room membership and the readiness toggle survive a reconnect on purpose — `finishHandshake()` re-requests the `List` (#220) and re-sends readiness.

**Password ownership:** the server password lives in main (`src/main/syncplay-credentials.ts`, `SyncplayPasswordVault`), persisted under the `syncplayPassword` store key — same treatment as `token` and `shikimoriCredentials`. Settings writes it with `syncplay:set-password` and can only ask *whether* one exists (`syncplay:has-password`); it is never read back into the renderer, so the input renders blank with a "saved" placeholder and a Clear button. `syncplay:connect` injects it into the outgoing config, which is the whole point: the join flows — the Watch Together view and the in-player join — send no password of their own and would otherwise connect unauthenticated (#216).

**Disconnect reasons (#213, #215):** the disconnected `status.error` is composed from the **last attempt only**, in precedence order: `lastServerError` (a non-escalated server `Error` frame, recorded only pre-`ready` and cleared in `finishHandshake()` — surfaced verbatim, e.g. `Room name is invalid`) → `watchdogDetail` (the watchdog's phase-naming timeout, outranking the transport error because the destroy that follows a fire manufactures one) → `lastSocketError` (the transport error, `Connection closed — connect ECONNREFUSED …`) → `PHASE_CLOSE_REASON` (keyed by `lastAttemptPhase` — the furthest phase the attempt reached, tracked in `setStatus()` against the five-phase whitelist and reset per attempt in `openSocket()`). An errorless close therefore always names its phase ("Server closed the connection during the TLS probe — …", "Connection to the server was lost") instead of a bare "Connection closed". The maxed-out variant prefixes `Max reconnect attempts reached — ` and uses each detail's short form (`no reply to TLS probe`, `connection lost`, …) so it stays one sentence. All three detail slots are per-attempt (reset in `openSocket()`, *not* `resetTransportState()`, which runs before the close handler composes the reason), and `status.error` is cleared (`error: undefined`) in the `openSocket()`, `finishHandshake()`, and user-`disconnect()` `idle` patches so a stale failure never renders next to a healthy or idle status. Per #119, "auto-reconnect disabled" is still never shown as a disconnect reason.

## File Identity

Syncplay clients identify "are we watching the same thing?" by file name + duration. We canonicalize our label to `"{animeName} - {episodeInt}"` so mpv/VLC users see a human-readable name, and duration is the HTML5 `<video>` `duration` rounded to the nearest second. For app-to-app sync (two instances of this app), we additionally stamp `features.animeDlAppMeta = { animeId, malId, episodeInt, translationId }` on outbound `Set.file` messages — the remote side uses this to auto-navigate when the other user advances to the next episode. Users on mpv/VLC don't emit this field, so auto-nav is a best-effort upgrade and the app falls back to identity-by-name for them.

## `ignoringOnTheFly` Bookkeeping

The protocol's anti-echo counter. Two independent counters (client-side and server-side) ride along on `State` messages. Local play/pause/seek increments `clientIgnoreCounter` and sends it on the next `State`; the server reflects the counter back. Until `pendingClientAck` drops to zero, inbound `State` messages that would override our local intent are dropped. This is the authoritative echo-suppression mechanism.

A local state only reaches this counter if it is genuinely ours (#220): pre-adoption element events don't bump it at all, because a pending ack makes `handleState()` drop the inbound states convergence depends on — a leaked bump desynced the session outright.

**Echo suppression (#220).** `suppressNextLocalEventUntil` (1500 ms after an apply) survives as a coarse backstop, but it is *not* what makes this correct: a seek on a network stream regularly completes after the window, and the element's `seeked` then escaped as our own — handing the peer back their own position with `doSeek`, dragging the room to a stale point. Suppression is therefore keyed on the value applied, not on the clock:

- renderer — `appliedSeekPosition` / `appliedPaused` record what an apply asked the element for; an event landing within `APPLIED_SEEK_EPSILON` (0.5 s) of it is the element realizing that request, not the user.
- main — `sendLocalState()` drops a `seek` within `ECHO_SEEK_EPSILON_S` of `lastAppliedRemotePosition`, the position it handed the renderer. Deliberately *not* the room's projected position, which drifts as the room plays.

## Heartbeat + RTT Compensation

A 1 s heartbeat (`setInterval` in main) sends the current `{paused, position}` regardless of local user input — this is how a stable idle state propagates and stays calibrated. Position source is a renderer-pushed snapshot via unthrottled `syncplay:local-snapshot` IPC on 1 s cadence, so main never pokes into renderer video state.

**Spectator rule (#220):** the heartbeat may only assert a playstate we actually have. `lastSnapshotAt` records when the renderer last pushed — off the 1 s interval *and* off `timeupdate`, because `backgroundThrottling` can stretch a muted or occluded window's timers toward 1/min and silently demote an active viewer, while media events aren't timer-throttled; older than `PLAYBACK_STALE_MS` (5 s, 5× the push cadence) means nothing is driving playback here — the Watch Together view joins a room *before* any player exists, and closing the player stops the pushes while the connection lives on. In that state `buildPlaystate()` returns the room's own last known state (`lastRoomState`, recorded raw in `handleState()` ahead of the echo guards, advanced by wall time while the room is playing so we don't read as the lagging user), or `null` — a ping-only `State` that keeps RTT calibration alive while asserting nothing — until the server has reported one. Without this the initial `{position: 0, paused: true}` snapshot went out once a second and yanked the whole room back to 0 and paused it the moment someone opened the Watch Together view. Both fields are session-scoped (cleared in `tearDown()`, preserved across a reconnect, like `roomUsers`).

**Adoption gate (#220):** having a player isn't enough — a freshly mounted `<video>` reports `{0, paused}` until the first remote `State` seeks it, and the renderer pushes that snapshot on its 1 s timer, so the "Join & watch" path would re-create the same room reset through a *live* player. `isAdopted()` therefore withholds assertions until local playback has converged to within `ADOPT_TOLERANCE_S` (3 s — the same threshold the apply rule uses to decide a seek is needed, so at or under it the renderer wouldn't move us anyway); until then we mirror. With no room state we adopt only when the **roster says we're alone** — with peers listed, an empty `lastRoomState` means our heartbeat simply beat the server's first `State`, and asserting the fresh `{0, paused}` there is the same yank the gate exists to prevent. It latches once converged, so ordinary drift never demotes a live player back to mirroring, and it resets in `setFile()` on a *file identity* change, and in `updateSnapshot()` whenever a push arrives after a stale gap — reopening the *same* episode gets a fresh element at 0 under an identical `canonicalName`, which the identity check alone cannot see.

**Known gap:** a pause made *before* adoption is dropped, and the first remote `State` then resumes the element (`applyRemoteState` drives `paused` from the room), so a deliberate pause-on-arrival is undone rather than merely delayed. A loading element's `pause` is byte-identical to the user's, so it isn't separable by inspection; deferring it to the moment adoption latches would need the renderer to re-apply it, which is left for a follow-up. With no room state there is nothing to contradict, so the first user in a room adopts immediately. A pre-adoption `sendLocalState()` sends **nothing at all** — not even an ignore-counter bump. Those calls arrive from the element's own `play`/`pause`/`seeked` events, which a loading player fires at ~0 before any remote state has been applied (so the renderer's `suppressNextLocalEventUntil` window isn't up yet); asserting them reset the room on "Join & watch", and bumping `clientIgnoreCounter` made `handleState()` drop the very inbound states needed to converge, desyncing the session outright. Once converged, user play/pause/seek propagate normally.

**Intent, not the element (#220):** the renderer reports what *this user* wants the room to be doing, never `v.paused`. The readiness gate and `useMsePlayer`'s `waitForBufferAhead` both pause and resume the element on their own — reporting those stalled the whole room on every buffer refill. `intendedPaused` is adopted from an applied remote state or set by a real play/pause, falls back to the element until intent exists (`intentOr`), and feeds both the snapshot and explicit local states. Programmatic moves are flagged: the gate sets `appliedPaused` inline, the buffer refill calls `markProgrammaticPlayback()` (a `useMsePlayer` dep wired in `PlayerView`), and each flag is only set when the call will actually change the element — marking a `pause()` on an already-paused element fires no event, leaves the flag latched, and swallows the user's *next* real pause. Intent is recorded regardless of the 1500 ms suppression window: that window only gates *sending*, and gating intent on it left the heartbeat asserting "playing" under a paused element, so the next remote apply resumed it.

Each outbound `State` stamps `clientLatencyCalculation = now / 1000`. The server echoes it back in its next `State`; `serverRtt = now − lastClientLatencyCalculation`. Inbound remote positions are shifted by `+ serverRtt / 2` before applying, to account for wire delay.

## Apply Rule

On inbound `State`, the renderer compares remote vs. local:
- `paused` differs → call `play()` / `pause()`.
- `state.doSeek === true` **or** `|remote.position − local.currentTime| > 3.0` → set `currentTime = remote.position`. The 3 s tolerance prevents drift jitter from causing constant micro-seeks.

## Readiness Gate (Buffer Sync)

When either user runs out of MSE buffer (HTML5 `waiting` event, or the MSE respawn path's `waitForBufferAhead`), the renderer calls `syncplay:set-ready(false)` which emits `Set: {ready: {isReady:false, manuallyInitiated:false}}`. Main tracks readiness per user from `Set: {user:{X:{isReady:{…}}}}` broadcasts and from `List` messages. A user dot turns amber in the popover's member list. Main's `ownIsReady` outlives any one player while the renderer's copy is player-scoped and only pushes on a change, so `setFile()` clears a stale `false`: a player closed mid-buffer would otherwise pin the user as *Buffering* in every peer's roster and hold their ready gate down for the rest of the session.

Renderer gates playback locally: if any room member (including self) is `isReady: false`, `applySyncplayReadyGate()` calls `v.pause()` even when the last remote `State` said `paused: false`. The last remote play intent is remembered in `syncplayLastRemotePlaying`; when the last not-ready user flips back to ready, the gate calls `v.play()` automatically. This keeps two app instances locked together when one falls behind on download/decode, rather than ping-ponging pause/play broadcasts.

## Remote Episode Auto-Nav

When the remote user advances to a new episode (detected by `features.animeDlAppMeta.episodeInt` change on inbound `Set.file`), main broadcasts `syncplay:remote-episode-change` with `{ animeId, episodeInt, translationId }`. PlayerView checks `animeId` against its current anime:
- **Match** — walks `goToEpisode('next'|'prev')` in a loop until `activeEpisodeIndex` reaches the target. Reuses the normal episode-switch path (including translation resolution).
- **Mismatch or episode not in list** — toast only. The app can't navigate to an anime that isn't loaded in the current view.

## Join Flow (WatchTogetherView, #213)

**Roster (#220):** membership comes from two sources, and only one of them arrives unasked. The server *broadcasts* `Set: {user:{X:{room, event?, file?}}}` for changes that happen while we're connected, but people already sitting in the room generate nothing — so `finishHandshake()` sends `{List: null}` to request the full roster (and re-requests it on every reconnect, which is how membership resyncs after a drop). Without that request a joiner saw "Room is empty — you're the first one here" in a room with people in it. The `List` reply is keyed by room and covers **every room on the server**, so `pickOwnRoom()` takes only ours — by the name the server seated us in (`handleHello` adopts a canonicalized `room.name`), falling back to the sole entry when the payload has exactly one and **adopting that entry's key** into `config.room`, so the roster and the `Set` filter below key off one string. `handleList` and `Set.file` share `extractAppMeta()`: a peer whose `animeDlAppMeta` doesn't survive the parse is listed but gets no "Join & watch" button, so both paths must read it identically. The roster's file shape differs from the broadcast's in one place: the server writes `file: {}` — never null, never absent — for a watcher with nothing loaded, so `handleList` maps a nameless file back to `null` (the `Set` path omits a falsy file and can't reach it).

**Room scoping on the `Set` path (#230).** With `isolateRooms` off — the reference server's default — `Set: {user}` is broadcast to *every* room on the server, so `handleSet()` filters each `user[X]` entry against `config.room` before acting on it. The filter is **ordered**, not a flat "ignore other rooms", because a peer switching out reaches us as a lone entry naming their **destination** with no `left` event (the server moves the watcher before broadcasting the switch):

0. **Self is exempt** — never filtered, never skipped. Our own file push is echoed back to us without sender exclusion, and `absorbRemoteFile()` is what keeps our roster row's file current between `List` replies. A self entry naming another room is not something a reference server can emit, so it is ignored rather than adopted (see [#230](https://github.com/mikkerlo/anime-downloader/issues/230) for the adopt-and-re-`List` design held in reserve).
1. **Room absent or equal to ours** — processed as before. Additionally, an entry carrying a room but neither `event` nor `file` is a switch *into* our room: the peer is seated and announced. The `file` exclusion matters — `sendFileUpdate` also emits `{room, file}` with no `event`, on the hot path, and `absorbRemoteFile()` already announces `X switched to "…"` and owns the seating there.
2. **Room differs and we have the user seated** — the switch-out frame: remove and emit `X left the room`. Runs *before* the `file` branch, or a frame carrying both would re-seat the user it just removed.
3. **Room differs and the user is unknown** — the whole entry is dropped, `file` and `isReady` included.

There is deliberately no top-level `Set: {room}` handler: that field is a client→server command, and honouring an unsolicited one would rewrite the filter's reference name mid-session and re-expose every stranger. `handleHello` is the only place a room name is adopted from the server, plus `pickOwnRoom`'s fallback above.

**Known gap — peer readiness is a join-time snapshot.** Live readiness travels as a *top-level* `Set: {ready: {username, isReady, manuallyInitiated, setBy}}` (reference `protocols.py` `sendSetReady`, broadcast on every join and toggle), which `handleSet()` does not parse; the `payload.user[X].isReady` branch it does have is dead code against a real server. Peer `isReady` therefore only ever comes from the initial `List`, so a peer's amber dot and its effect on the local ready gate never update after join. Fixing it is ~10 lines in `handleSet` plus tests, and is the highest-value follow-up on the syncplay backlog.

A dedicated **Watch Together** sidebar view lets a user join a room *before* opening the player. It connects with the saved server/username settings, renders the live member list (username, ready dot, current file) from the `useSyncplayStore` Pinia store, and — for members whose `Set.file` carried `animeDlAppMeta` — offers **"Join & watch"**: the room state is re-fetched at click time (the peer may have advanced episodes), then `useOpenEpisode` resolves the anime + a CDN stream for the peer's `(animeId, episodeInt, translationId)` and opens the built-in player. mpv/VLC peers (no app metadata) are listed but not auto-joinable.

Connection handoff: the room connection lives in main and outlasts view mounts. `useSyncplayClient` never assumes it owns the lifecycle — on mount it re-seeds the store and, if the session is already `ready`, immediately pushes the current file (the transition-into-ready watcher never fires in that case; without the push the joiner would stay invisible to the host). `onDurationChange` re-pushes once real duration is known.

Renderer state ownership: `useSyncplayStore` (`src/renderer/src/stores/syncplay.ts`) singleton-owns the `connection-status` and `room-users` subscriptions, seeded from `syncplay:get-status`/`syncplay:get-room-users`; WatchTogetherView and the player's `useSyncplayClient` both read from it. Player-scoped subscriptions (remote-state, room-event, trace, remote-episode-change) stay in `useSyncplayClient`.

## IPC Surface

Main-side handlers (see [IPC Handlers](./ipc.md)): `connect`, `disconnect`, `set-file`, `local-state`, `local-snapshot`, `set-ready`, `get-status`, `get-room-users`, `set-password`, `has-password`. Broadcasts: `connection-status`, `remote-state`, `room-users`, `room-event`, `remote-episode-change`. Settings tab "Watch Together" in `SettingsView.vue` persists host/port/room/username/autoReconnect under the `syncplay` electron-store key, and the password separately under `syncplayPassword` (see Password ownership above). The live connection itself is **not** persisted: users must rejoin after a restart.

Debug tracing gated by `SYNCPLAY_DEBUG=1` env var — dumps every inbound/outbound JSON message and state transition to the main process log.
