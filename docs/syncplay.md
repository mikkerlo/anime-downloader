# Watch Together (Syncplay)

Two (or more) users watching the same anime together over the Internet, staying in lockstep on playback position. Compatible with the [Syncplay](https://syncplay.pl) protocol — connects to community servers (`syncplay.pl:8999` default) and interoperates with the reference `syncplay.pl` desktop client (mpv/VLC), so a friend can watch along from any player Syncplay supports.

## Module: `src/main/syncplay.ts`

Standalone TCP/TLS client. **TLS-only:** `net.Socket` opens the TCP connection, the very first message we send is the Syncplay TLS probe `{TLS:{startTLS:'send'}}` (the key must be `startTLS` — servers close the socket immediately on anything else), and only after the server replies `{TLS:{startTLS:'true'}}` and `tls.connect({ socket })` finishes its handshake (with `rejectUnauthorized` left at its default `true`) do we send the `Hello` message containing username/password. The server password travels as an **MD5 hex digest** (`md5Hex()` in the module) — Syncplay servers MD5 their own `--password` at startup and compare digests, so sending it plaintext is always rejected with "Wrong password supplied"; MD5 is the protocol's wire format, not a security claim, since the session is already inside TLS. Servers that do not support STARTTLS — or whose certificate fails verification against `host` — drop the connection with a clear error. Line-delimited JSON (each message is one JSON object followed by `\r\n`). All protocol-level concerns live here — the renderer only emits high-level playback events.

The `Hello` also carries a claimed protocol **version** and a **`features`** object. The version (`SYNCPLAY_WIRE_VERSION`, currently `1.7.6`) is a deliberate wire-protocol claim rather than our app version — it gates two things server-side: the MOTD "upgrade available" nag, prepended when we fall below the server's `RECENT_CLIENT_THRESHOLD` (which upstream bumps to each release's own version, so this needs a periodic bump — headroom is zero by construction), and `Chat` delivery, gated on a raw *string* compare against `CHAT_MIN_VERSION` (`1.5.0`), which is why a future `1.10.0` would pass the MOTD gate's tuple compare and silently kill inbound chat. It must stay strictly numeric dotted; the server parses each component outside its error handling, so a suffixed value kills the handshake. No `realversion` is sent — the server prefers it over `version` when present. The `features` object declares six flags — `sharedPlaylists: false`, `chat: true`, `featureList: false`, `readiness: true`, `managedRooms: false`, `persistentRooms: false` — on the criterion that a flag is `true` **iff this client actually reads or writes that feature's frames**, which is why `chat` is `true` (inbound `Chat` is consumed and toasted, though we never send one) and `readiness` is `true` (`sendSetReady()` writes, and peer state is read from the `List` roster). All six keys stay present as explicit `false` rather than being omitted: the server defaults a missing key to false, but an absent or empty `features` object makes it derive the whole set from our version string instead. Two keys are absent on purpose — `uiMode`, because declaring it opts us into unsolicited roster pushes on rooms-DB servers, and `setOthersReadiness`, because advertising it suppresses the server's own "X set Y as ready" notice, the user's only explanation for a peer changing their ready state.

State machine: `idle → connecting → tls-probing → tls-handshake → hello-sent → ready → (reconnecting) → disconnected`. On transport error: exponential backoff reconnect, max 5 attempts. On protocol error (wrong password, bad handshake, server refused TLS, protocol garbage): abort without retry — a non-Syncplay server will not become one on retry. The handshake watchdog (#215) is explicitly *not* in that list: 8 s of pre-`ready` silence (strictly below the Settings test button's 10 s renderer timer, so the informative message always wins the race; also always ahead of the OS SYN timeout, deliberately superseding `connect ETIMEDOUT`) records a neutral, phase-naming detail ("No reply received in 8s while in `tls-probing`"; in `connecting`, where nothing has been sent yet, "Could not establish a TCP connection within 8s — the host may be unreachable or the port filtered"), emits it as a `warn` room-event, and destroys the socket — the normal `close` → reconnect path then runs, because a transient hang is exactly what auto-reconnect exists for. For a watchdog-fired attempt, `onSocketError()` suppresses both the fatal-TLS `ECONNRESET` classifier (destroy-before-`secureConnect` manufactures that precise signature) and the fall-through `Connection error` room-event, so the app's own destroy is never reported as the server's fault. Garbage detection (#215) is pre-`ready` only: 5 JSON parse failures in one attempt, or 64 KB received without a single valid message (`GARBAGE_PARSE_FAILURE_LIMIT`/`GARBAGE_BYTE_CAP`), abort with "Server sent data that is not Syncplay protocol — is this a Syncplay server?"; post-`ready` a corrupt line keeps the skip-and-log behavior so a live session doesn't die on one bad frame. The counters deliberately survive the TLS upgrade — plaintext-phase garbage counts toward the same attempt's verdict.

**Per-socket vs per-session state:** `resetTransportState()` clears everything that belongs to one socket — `rxBuffer`, `tlsUpgraded`, the `ignoringOnTheFly` counters, `serverRtt`, the pending server ping timestamp and its arrival time (`lastServerLatencyCalculation`/`lastServerLatencyArrivalMs`, #231 — a timestamp minted by the previous socket would report the outage duration as the RTT on the first echo), the garbage-detection counters and the watchdog *timer* (#215) — and is called both by `tearDown()` and by the reconnect path in `onSocketClose()`. The watchdog's `watchdogDetail`/fired flag are deliberately **not** in this list: `onSocketClose()` calls `resetTransportState()` before it composes the disconnect reason, so a detail parked here would be erased on every path that could read it — they reset per attempt in `openSocket()` with the other detail slots instead. The reconnect path deliberately does *not* go through `tearDown()`, so it must reset this itself: a stale `tlsUpgraded` makes `handleTls()` treat the retry's probe reply as a spurious post-upgrade message, `tls.connect()` is never called again, and the client hangs in `tls-probing` until the server times it out (#216). Room membership and the readiness toggle survive a reconnect on purpose — `finishHandshake()` re-requests the `List` (#220) and re-sends readiness. What does *not* survive is `rosterReceived` (#236), the flag that says the server has told us who is in our room: the membership list is still the best answer we have, but a roster minted before an outage cannot list a peer who joined during it, and the adoption gate below reads it as permission to assert. It is cleared here and re-earned from the reply to that re-request, at a cost of one round trip of ping-only frames per attempt. This guards the *unlatched* client only, and deliberately so: `playbackAdopted` is session-scoped — no socket path clears it, so a reconnect keeps it (#227 — same player, same room) and `isAdopted()` returns on its first line without ever consulting `rosterReceived`. A client that had already adopted before the outage therefore still asserts its position at a peer who joined during it; what clearing the flag closes is the shape where nothing has latched yet — connected, alone-roster, no live player, socket drops, a peer joins, and a freshly opened player's first element event arrives before the new `List` reply. The `List` poll timer is per-socket too, but it is a *timer*, not state — like the heartbeat it is stopped in both `tearDown()` and `onSocketClose()` and restarted by `finishHandshake()`, and `startListPolling()` stops any existing interval first, so a reconnect can never leave two running (#216's failure class).

**Password ownership:** the server password lives in main (`src/main/syncplay-credentials.ts`, `SyncplayPasswordVault`), persisted under the `syncplayPassword` store key — same treatment as `token` and `shikimoriCredentials`. Settings writes it with `syncplay:set-password` and can only ask *whether* one exists (`syncplay:has-password`); it is never read back into the renderer, so the input renders blank with a "saved" placeholder and a Clear button. `syncplay:connect` injects it into the outgoing config, which is the whole point: the join flows — the Watch Together view and the in-player join — send no password of their own and would otherwise connect unauthenticated (#216).

**Disconnect reasons (#213, #215):** the disconnected `status.error` is composed from the **last attempt only**, in precedence order: `lastServerError` (a non-escalated server `Error` frame, recorded only pre-`ready` and cleared in `finishHandshake()` — surfaced verbatim, e.g. `Room name is invalid`) → `watchdogDetail` (the watchdog's phase-naming timeout, outranking the transport error because the destroy that follows a fire manufactures one) → `lastSocketError` (the transport error, `Connection closed — connect ECONNREFUSED …`) → `PHASE_CLOSE_REASON` (keyed by `lastAttemptPhase` — the furthest phase the attempt reached, tracked in `setStatus()` against the five-phase whitelist and reset per attempt in `openSocket()`). An errorless close therefore always names its phase ("Server closed the connection during the TLS probe — …", "Connection to the server was lost") instead of a bare "Connection closed". The maxed-out variant prefixes `Max reconnect attempts reached — ` and uses each detail's short form (`no reply to TLS probe`, `connection lost`, …) so it stays one sentence. All three detail slots are per-attempt (reset in `openSocket()`, *not* `resetTransportState()`, which runs before the close handler composes the reason), and `status.error` is cleared (`error: undefined`) in the `openSocket()`, `finishHandshake()`, and user-`disconnect()` `idle` patches so a stale failure never renders next to a healthy or idle status. Per #119, "auto-reconnect disabled" is still never shown as a disconnect reason.

## File Identity

Syncplay clients identify "are we watching the same thing?" by file name + duration. We canonicalize our label to `"{animeName} - {episodeInt}"` so mpv/VLC users see a human-readable name, and duration is the HTML5 `<video>` `duration` rounded to the nearest second. For app-to-app sync (two instances of this app), we additionally stamp `features.animeDlAppMeta = { animeId, malId, episodeInt, translationId }` on outbound `Set.file` messages — the remote side uses this to auto-navigate when the other user advances to the next episode. Users on mpv/VLC don't emit this field, so auto-nav is a best-effort upgrade and the app falls back to identity-by-name for them.

## `ignoringOnTheFly` Bookkeeping

The protocol's anti-echo counter. Two independent counters (client-side and server-side) ride along on `State` messages. Local play/pause/seek increments `clientIgnoreCounter` and sends it on the next `State`; the server reflects the counter back. Until `pendingClientAck` drops to zero, inbound `State` messages that would override our local intent are dropped. This is the authoritative echo-suppression mechanism.

**The server counter wins outright (#232).** There are two ways `pendingClientAck` drops to zero, not one: a matching `client` echo, *or* any inbound frame carrying an `ignoringOnTheFly.server` key, which zeroes it unconditionally — reference behaviour (`protocols.py:287-288`, whose `not self.clientIgnoringOnTheFly` gate at `:296` then lets the forced state through). Both happen in `handleState()` **above** the drop guard, because that guard returns and anything below it is a no-op for the case this exists to serve. Without the zeroing a *peer's* forced `State` crossing our own unacked change is eaten by the guard, and a forced `State` is one-shot — the server never resends it. In the forward-seek direction that loss is unrecoverable rather than late: the room re-derives its position from `min(watchers)` (`server.py:597-604`), our un-applied earlier position wins, `_setBy` becomes us, and our own self-`setBy` guard then drops the periodic too — so one dropped frame silently reverts the peer's seek for the whole room. (A backward seek converges only because the seeker happens to be the `min`; that is coincidence, not recovery.)

The frames whose behaviour actually changes are those carrying a `server` key with **no** matching `client` echo. A forced update *we* caused comes back carrying both (`protocols.py:758-760`), so the client-echo arm was already clearing the guard on that frame. The accepted trade-off is therefore narrow: we give up echo protection for the ~1 RTT between our own assertion going out and the server echoing it back — our change is already on the wire by then, so all we stop doing is suppressing inbound states. The two arms stay two independent `if`s rather than the reference's `if`/`elif`: once the zeroing runs, `pendingClientAck` is 0 and the server only writes a `client` key when its own counter is truthy, so the second arm can never match.

A local state only reaches this counter if it is genuinely ours (#220): pre-adoption element events don't bump it at all, because a pending ack makes `handleState()` drop the inbound states convergence depends on — a leaked bump desynced the session outright.

**Echo suppression (#220, #239).** `suppressNextLocalEventUntil` (1500 ms after an apply) survives as a coarse backstop **for `play` / `pause` only** — those have no applied value to key on. It no longer gates `seek` at all (#239): a seek on a network stream regularly completes after the window, and the element's `seeked` then escaped as our own — handing the peer back their own position with `doSeek`, dragging the room to a stale point. Worse in the other direction, the window dropped *every* seek inside it, including the user's own to a position nobody applied, so a Skip OP click landing just after a remote apply (or inside the 1500 ms the readiness gate re-arms on **every** buffer refill) moved only the local player and the room never heard about it. Seek suppression is therefore keyed on the value applied, not on the clock:

- renderer — `appliedSeekPosition` / `appliedPaused` record the move the app made and is still waiting for the element to realize. `appliedSeekPosition` is a `{ value, expiresAt, anyValue }` mark in **two kinds** (#239): a remote apply arms `anyValue: false`, matched by value within `APPLIED_SEEK_EPSILON` (0.5 s) — deliberately strict, because #240 makes it the sole renderer-side seek-echo guard for a deferred apply, and a value-agnostic one would swallow the user's first real seek after every apply. It is armed at **write** time and not at arrival — on the immediate path and the deferred one alike (#240) — with `Math.max(0, state.position)`, the same number main emitted, so the renderer mark and main's backstop below agree on one value; a parked state can be superseded, and its write fires arbitrarily far outside any wall-clock window. `markProgrammaticSeek` arms `anyValue: true`, consuming the next `seeked` whatever position it reports. It is bounded by `APPLIED_SEEK_TTL_MS` (15 s, floored by the transcode respawn's buffer-ahead wait) rather than by a wall clock — a short window is the same fragility this keying exists to remove — and is cleared on a consume or on expiry, **never on a mismatch**: between an apply and its echo any programmatic site can fire a `seeked`, and consuming the mark there let the real echo escape (#224's loop).
- main — `sendLocalState()` drops a `seek` within `ECHO_SEEK_EPSILON_S` of `lastAppliedRemotePosition`, the position it handed the renderer. Deliberately *not* the room's projected position, which drifts as the room plays. `handleState()` arms that target only for a state that would actually **move** the element, under the same rule the renderer applies with — `doSeek === true || |snapshot.position − compensated| > ADOPT_TOLERANCE_S` (#236). Armed on *every* inbound state it sat pointing at the room's resting position after states that changed nothing — refreshed once a second in a paused room — and swallowed any genuine user seek landing within 0.5 s of it. A state that moves nothing fires no `seeked`, so it has no echo to suppress; a target armed by an earlier state is left in place, because that one is still owed its event. The predictor is main's own snapshot rather than the element's `currentTime`, so near the 3 s boundary the two can disagree by up to one snapshot cadence — wider under #240, which defers the write to `loadedmetadata` — and main can decline to arm for a state the renderer does apply. The renderer's value-keyed mark still suppresses that echo: the loss is main's belt, not both layers. The arming is also **unexpired**, which leaves one shape open: a genuinely-moving state arms the target, the renderer swallows the resulting `seeked` value-keyed before `sendSyncplayLocalState` runs, so neither retirement in main fires and the target stays armed until the next local assertion of any cause or the session ends. Accepted residue, and strictly narrower than re-arming every second.

## Heartbeat + RTT Compensation

A 1 s heartbeat (`setInterval` in main) sends the current `{paused, position}` regardless of local user input — this is how a stable idle state propagates and stays calibrated. Position source is a renderer-pushed snapshot via unthrottled `syncplay:local-snapshot` IPC on 1 s cadence, so main never pokes into renderer video state.

**Three outbound `State` paths, not one.** The heartbeat is the only *periodic* sender, but two others emit the same frame type:

| Path | Trigger | Carries a playstate? |
|---|---|---|
| `sendStateMessage()` on the 1 s `setInterval` | timer | yes, when `buildPlaystate()` has one |
| `sendStateMessage()` from `sendLocalState()` | a real local play/pause/seek, post-adoption | yes |
| `sendAck()` from `handleState()` (#232) | an inbound `ignoringOnTheFly.server` counter | **never** |

`sendAck()` is a dedicated emitter rather than a flag on `sendStateMessage()`, so "the ack can never carry a playstate" is a property of the code instead of something a caller must remember. It matters: on the tick the counter lands the renderer has not applied the forced state yet (`remote-state` is emitted further down `handleState()`, the element takes hundreds of ms to seek, and `snapshot` only refreshes on the renderer's 1 s push), and the adoption gate cannot withhold the stale value because `playbackAdopted` latches. That same frame is the one lifting the server's ignore flag (`protocols.py:775-777`, ahead of the `:788` gate), so the first playstate the server would accept from us is the stale one — and `Room.getPosition()` takes `min(watchers)`, so a stale-behind position drags the whole room back.

This is a deliberate **divergence** from the reference, not convergence: the reference client does ship a playstate on its echo frame (`protocols.py:304-305` — both disjuncts are true right after the zeroing). We diverge because our seek latency and 1 s snapshot cadence make our stale window far wider than mpv's, and because a playstate-free `State` is provably inert server-side (`updateState(None, None, None, …)` reads `__hasPauseChanged(None)` as False and skips `setPosition`).

The ack fires from *inside* the counter branch, not at the end of `handleState()`: four early returns sit in between, and the self-`setBy` one is the dominant path for a counter-bearing frame — the server broadcasts a forced update back to the setter too (no sender filter in `broadcastRoom()`), so the scrubbing user's own connection is precisely the deaf one. It is gated on `status.state === 'ready'` (`dispatch()` has no readiness gate, so `handleState()` genuinely runs mid-handshake, and again in the reconnect window); a counter arriving while gated out is not lost, because `sendStateMessage()`'s own drain carries it on the first heartbeat once ready. It does *not* run during teardown — `tearDown()` calls `socket.removeAllListeners()` before `destroy()` and `resetTransportState()` empties `rxBuffer`, so no further frame reaches the parser. Cost is one extra frame per forced update — while `serverIgnoringOnTheFly != 0` the server suppresses its own periodic `State` and only increments on `forced`, so it cannot loop. Like every other sender, `sendAck()` builds its `latencyCalculation` echo through `consumeServerLatencyEcho()`, which is what keeps #231's consume-once guarantee true across two emit sites; the timestamp arrives on the very frame the ack answers, so its hold is sub-millisecond.

**Spectator rule (#220):** the heartbeat may only assert a playstate we actually have. `lastSnapshotAt` records when the renderer last pushed — off the 1 s interval *and* off `timeupdate`, because `backgroundThrottling` can stretch a muted or occluded window's timers toward 1/min and silently demote an active viewer, while media events aren't timer-throttled; older than `PLAYBACK_STALE_MS` (5 s, 5× the push cadence) means nothing is driving playback here — the Watch Together view joins a room *before* any player exists, and closing the player stops the pushes while the connection lives on. In that state `buildPlaystate()` returns the room's own last known state (`lastRoomState`, recorded raw in `handleState()` ahead of the echo guards, advanced by wall time while the room is playing so we don't read as the lagging user), or `null` — a ping-only `State` that keeps RTT calibration alive while asserting nothing — until the server has reported one. Without this the initial `{position: 0, paused: true}` snapshot went out once a second and yanked the whole room back to 0 and paused it the moment someone opened the Watch Together view. Both fields are session-scoped (cleared in `tearDown()`, preserved across a reconnect, like `roomUsers`).

**Known gap — a paused hidden player goes stale (#227, pinned not fixed).** `timeupdate` does not fire while the element is *paused*, so a paused player has only the throttled 1 s interval, and a window hidden for **minutes** (Chromium clamps to ~1 Hz first and drops toward ~1/min only under intensive throttling) does cross `PLAYBACK_STALE_MS` and get demoted to the spectator mirror. The de-adoption is a second, later step — it lives only in `updateSnapshot()`, which by construction cannot run during the gap — so `playbackAdopted` flips on the **first push after the window is unhidden**, not at the 5 s mark. Room-state-wise this is harmless: the mirror makes no pause claim and its forward-projected position is never below the room, so it cannot drag `Room.getPosition()`'s `min()`. It is not free, though. On the first post-unhide push we de-adopt, and re-adoption is a drift test: if the room played on while we sat paused, or — spectating *alone* in a paused room — the server's own forward compensation walked `lastRoomState` away from our stationary position (the "known consequence" documented at `buildPlaystate()`), drift exceeds `ADOPT_TOLERANCE_S` and the user's first post-unhide action is dropped until a remote apply seeks us back. Main records those crept States and returns at the `setBy`-less guard, so nothing corrects the element and the drift is invisible until the user acts. Fixing it needs a snapshot source that survives background throttling while paused, which is a separate issue; the five cases under "a paused hidden player goes stale and recovers" in `syncplay-room-presence.test.ts` pin the behaviour as it stands.

**Adoption gate (#220):** having a player isn't enough — a freshly mounted `<video>` reports `{0, paused}` until the first remote `State` seeks it, and the renderer pushes that snapshot on its 1 s timer, so the "Join & watch" path would re-create the same room reset through a *live* player. `isAdopted()` therefore withholds assertions until local playback has converged to within `ADOPT_TOLERANCE_S` (3 s — the same threshold the apply rule uses to decide a seek is needed, so at or under it the renderer wouldn't move us anyway); until then we mirror.

Three tests, in order (#236): **latched** → **the roster says we're alone** → **drift**.

| | roster: alone | roster: peers listed | roster not yet received |
|---|---|---|---|
| **no room state** | `true` — we establish the room | `false`, ping-only frame | `false`, ping-only frame |
| **room state** | `true` | `drift <= ADOPT_TOLERANCE_S` | `drift <= ADOPT_TOLERANCE_S` |

The roster test is a *positive* signal, not a fallback for "no room state yet", and its **absence** is what holds us off. Both directions of the older shape were wrong. Nothing distinguished "the roster is empty" from "the roster hasn't arrived" — `tearDown()` empties `roomUsers`, `finishHandshake()` only *requests* the roster, and `updateOwnReadinessInRoom()` has already seated *us* — so the peer filter read zero and adoption latched inside the handshake window on any element event that landed there. And nesting the test under "no room state" made it unreachable in the case it was written for: on a reference server the first `State` arrives ~100 ms after login (`server.py:737` schedules it via `callLater(0.1)`; the `LoopingCall` at `:841-843` fires immediately, `SERVER_STATE_INTERVAL` is 1 s) while our own heartbeat's first tick is `HEARTBEAT_MS` after the same `Hello`, and both carry the same one-way latency — so `lastRoomState` is set long before the roster test could run. A user genuinely **alone** at, say, 600 s then fell through to a drift of 600 and never adopted: `buildPlaystate()` mirrored the room forever, `Room.getPosition()`'s `min()` over watchers (just us) kept the room pinned near 0, and the next peer to join adopted at *their* drift of 0 and dragged the first user back — the #220 yank with the roles reversed, on every "connect from inside a player to an empty room". The drift path stays unconditional, so a server that never answers `{List: null}` still adopts once the renderer's apply converges us; the one quadrant that now answers `false` where it used to answer `true` is "no roster **and** no `State`", where the failure is silence rather than a wrong assertion.

**The latch is projected to the renderer, together with the room's pause flag (#228).** `setStatus()` and `getStatus()` overlay `playbackAdopted: this.playbackAdopted` and `roomPaused: this.lastRoomState?.paused === true` on every emit and every read. Both are **projections, never stored fields**: `tearDown()` clears the latch and nulls `lastRoomState` with no `setStatus()` call anywhere on that path, so a mirrored copy would announce session 1's `true` through the whole of session 2's pre-adoption window — the exact window the renderer reads it in. Since neither underlying value changes on a status *transition*, `emitStatusIfProjectionChanged()` compares the projections against the last **emitted** status and re-emits (`setStatus({})`, so `state`/`error` are preserved) on a difference; it is re-entrancy-guarded and called from two places — the heartbeat tick **after** `sendStateMessage()`, so the latch that call's own `buildPlaystate()` → `isAdopted()` just flipped announces on the same tick as the assertion it belongs to, and `handleState()` right after the `lastRoomState` write, which is above the `setBy`-null / self-`setBy` / unacked guards that drop the very frames a held pause is waiting for. Cost: at most one extra `connection-status` per heartbeat plus one per inbound state, and only on a real difference.

It latches once converged, so ordinary drift never demotes a live player back to mirroring. It resets in `updateSnapshot()` whenever a push arrives after a stale gap, and in `setFile()` when **a new player is announcing itself** — `identityChanged || file.newPlayer === true` (#236). Neither half says that alone: file identity misses a same-episode reopen (`canonicalName` is `"{animeName} - {episode}"` with no translation component, so close-player → pick another translation → reopen re-pushes a byte-identical name at a fresh `<video>` at 0), and the snapshot clock still reads "live" for the whole of `PLAYBACK_STALE_MS` after the previous player closed — precisely the window that reopen lands in, where a surviving latch let the new element's startup `play`/`pause`/`seeked` assert `{0, doSeek: true}` at the room. `newPlayer` is an optional field on the `syncplay:set-file` payload, set by the composable on the **first** push of each mount (mount-scoped, not `onMounted`-scoped, so a player that mounts before the session is `ready` still marks its first announcement) and absent on every later push from that mount. It never reaches the wire — `sendSetFile()` builds the outbound `Set: {file}` field by field.

**Pending-pause precedence (#228):** a pause made *before* adoption used to undo itself — the next inbound playing state resumed the element through the apply (`intendedPaused` clobber + `v.play()`) and through the ready gate, whose `syncplayLastRemotePlaying` the user's own pause could not clear (that mirror write was gated on the 1500 ms wall-clock window every apply re-arms at ~1 Hz during convergence). The rule now is **a pending user pause outranks the room until it has had its chance to reach the room**: the renderer's `pendingUserPause` flag makes the gate's `shouldPlay` false and makes a playing apply hold — see the Apply Rule below.

**Adoption is not the end of the hold, and deliberately not a clear path.** Post-adoption a local assertion arms `pendingClientAck` and `handleState()` drops inbound states until the server acks it; that protection is switched off pre-adoption on purpose (a bump would starve convergence — see the paragraph below). A pause held *through* the latch flip never armed that counter and never will: post-adoption it is asserted only by the heartbeat, which reads `pendingClientAck` but never writes it. So at the moment the latch flips, a playing state already on the wire would replay the whole bug one RTT later. The hold therefore ends on the first of: a real `play` from the user; an inbound state with `paused: true`; the `roomPaused` projection going `false → true` (an **edge**, not a level — carrying the mirror repair `syncplayLastRemotePlaying = false`, because the hold *masked* that mirror rather than undoing it, and a bare clear would let the next gate entry resume the pause); `PENDING_PAUSE_MAX_MS` (8000) elapsing; an episode/translation switch (a new episode deliberately auto-resumes the binge through the gate); or the `idle`/`disconnected` session reset. `roomPaused` is the normal terminator and the timer only the backstop — which matters because the renderer almost never sees the echo of its own pause (`setBy`-null and self-`setBy` states are dropped, and during a hold the server's `min()` re-election keeps `setBy` ours), so main projects `lastRoomState.paused`, recorded above those guards, as `roomPaused`.

Held seeks are still applied — withholding them would stall the very adoption the hold waits for, since `isAdopted()`'s drift latch reads the position the renderer reports — so the hold is a local divergence with a deadline: the paused frame jumps forward until the assertion lands. The happy path ends at ~4–5 s through `roomPaused`, the failure path at 8 s with "The room kept playing — your pause didn't stick" (shown only if at least one playing state was actually *held*; an expiry that held nothing is silent, and the "Pausing once synced with the room…" toast fires on the first held state, not on the press, riding the hold's remaining window). Reference precedent for announcing a deliberate override of the user's own pause/play: the official client's `ready-to-unpause` notification.

**Residual (unchanged, out of scope):** a *post*-adoption pause landing inside the 1500 ms send window never reaches main and is asserted only by the next heartbeat; an inbound playing state in that ≤1.5 s gap still clobbers it. That wants a `cause === 'pause'` relaxation of the send gate, not this flag. A pre-adoption `sendLocalState()` sends **nothing at all** — not even an ignore-counter bump. Those calls arrive from the element's own `play`/`pause`/`seeked` events, which a loading player fires at ~0 before any remote state has been applied (so the renderer's `suppressNextLocalEventUntil` window isn't up yet); asserting them reset the room on "Join & watch", and bumping `clientIgnoreCounter` made `handleState()` drop the very inbound states needed to converge, desyncing the session outright. Once converged, user play/pause/seek propagate normally.

**Intent, not the element (#220):** the renderer reports what *this user* wants the room to be doing, never `v.paused`. The readiness gate and `useMsePlayer`'s `waitForBufferAhead` both pause and resume the element on their own — reporting those stalled the whole room on every buffer refill. `intendedPaused` is adopted from an applied remote state or set by a real play/pause, falls back to the element until intent exists (`intentOr`), and feeds both the snapshot and explicit local states. Programmatic moves are flagged: the gate sets `appliedPaused` inline, the buffer refill calls `markProgrammaticPlayback()` (a `useMsePlayer` dep wired in `PlayerView`), and each flag is only set when the call will actually change the element — marking a `pause()` on an already-paused element fires no event, leaves the flag latched, and swallows the user's *next* real pause. The same rule covers a call that was *meant* to change the element and then didn't: every `v.play()` this app makes on the room's behalf retracts its mark from the promise's `catch` — the ready gate's, `useMsePlayer`'s two refill resumes, and (since #236) `applyRemoteState`'s, which was the one mark site that structurally could not retract. Left latched, a remote resume refused by autoplay policy pinned `appliedPaused = false` for good and `onLocalPlay()` read the user's next real play as that echo, so it never reached the room.

**The room-mirror writes follow the same classification rule as intent (#228).** Both `onLocalPlay()` and `onLocalPause()` write `syncplayLastRemotePlaying` / `syncplayLastAppliedPaused` / `syncplayPausedBy` **unconditionally** past the `appliedPaused` echo check — the wall-clock window no longer gates them, only *sending*. Anything past that check is the user, by the same classification the `intendedPaused` write already relies on; gating it meant the mirror said "the room is playing" straight through the user's own pause, which is the second resume path #228 closes. The two halves ship together: relaxing the pause side alone leaves a stale `false` behind that the gate reads on the user's own immediate resume, and "press play right after pausing" re-pauses itself.

Two consequences the relaxation buys, both load-bearing:

- **PlayerView's teardown `pause()` must be marked** (`markProgrammaticPlayback(true)`, guarded on `!video.paused` by the "only flag a call that will actually change the element" rule). Unmarked it would now move room-mirror state — and post-adoption send a pause — on the way out of the player, i.e. closing the player would pause the room.
- **Any *future* unmarked programmatic `pause()`/`play()` at `readyState >= 1` becomes room-visible.** The `src`-reassignment family (the `wasPlaying` restores and `goToEpisode`'s plays) deliberately stays unmarked — marking them turns a self-healing flicker into a stuck pause through the echo-branch/gate interaction, and the right shape for that is a multi-slot/token marker owned by the #236 family — but a new site added without a mark is a room-visible move.

**Arming the hold is gated on `(getVideoEl()?.readyState ?? 0) > 0`,** and on the status projection `playbackAdopted !== true`. The `readyState` half is what excludes every reload-shaped implicit pause without any PlayerView plumbing: the media load algorithm resets `readyState` synchronously, and the `pause` event it queues — *if engines fire one at all; this is unverified against a real element, and the design is correct either way* — is delivered after that reset, as is the teardown pause's event (PlayerView runs `pause()` then `src=''`+`load()` before the task fires). The accepted residual is a genuine user pause on an element reporting `HAVE_NOTHING`: it does not arm, but inbound states are parked in that window anyway and the unpark clobbers intent, so pre-#228 behavior holds there. The `playbackAdopted` half scopes the device to the window where main asserts nothing — post-adoption it is redundant for what reaches the wire, and alone in a room (where the roster test adopts instantly) it would guarantee a failure toast nobody earned.

**Known residual — the playback mark is a single unidentified slot.** `markProgrammaticPlayback(null)` retracts only a *resume* mark, which is a heuristic rather than an identity: it closes the ordering where a `pause()` supersedes a marked resume, but not the one where a `play()` fires its `play` event (consuming its mark), a newer resume mark is installed, and only then does the first call reject because a later one interrupted it — that retraction clears a mark the element still owes an event for, and the next programmatic resume is read as user intent. Bounded by the same 1500 ms window. Making the mark identifiable (a token, so the compare-and-clear is exact) is #236's item 4, and it is deliberately still open: it changes the signature `useMsePlayer` and `PlayerView` wire through, and #228 adds mark sites to the same surface. Intent is recorded regardless of the 1500 ms suppression window: that window only gates *sending*, and gating intent on it left the heartbeat asserting "playing" under a paused element, so the next remote apply resumed it.

**Renderer session vs socket state (#227).** The composable's mutable state splits the same way main's does, and the `syncplayStatus` watcher is where both rules live:

- **Session-scoped** — cleared on `idle`/`disconnected`, **kept across `reconnecting`**: `intendedPaused`, `appliedPaused`, `appliedSeekPosition`, `suppressNextLocalEventUntil`, `lastSnapshotPushAt`, plus `syncplayLocalReady`, `syncplayLastRemotePlaying`, `syncplayLastAppliedPaused`, `syncplayPausedBy` and — since #228 — `pendingUserPause` with its 8 s timer and pending toast (room B must not inherit room A's hold, nor a timer that would toast a failure into a session that held nothing; the timer also joins the `onBeforeUnmount` cleanup). This is the renderer half of `tearDown()`, which clears `snapshot`/`lastRoomState`/`playbackAdopted` and which the reconnect path deliberately skips. A reconnect is the same room, the same player and the same user, and the element writes these markers stand for may still be in flight; a *session* end is room A handing over to room B, where a stale `intendedPaused` reports A's play state into B, `appliedPaused` swallows exactly one real play/pause, `appliedSeekPosition` swallows the first real seek for the rest of its 15 s TTL, `suppressNextLocalEventUntil` eats both the send and the `pausedBy` attribution of the first intent recorded inside the dead window, and `lastSnapshotPushAt` drops the first `timeupdate` snapshot when the re-join lands inside `SNAPSHOT_MIN_INTERVAL_MS`.
- **Per-socket** — cleared on `reconnecting` **and** at session end: `pendingRemoteState` / `remoteStateApplied`, via `resetRemoteStateTracking()` (#240). Not a contradiction with the rule above but the same distinction main draws between `tearDown()` and `resetTransportState()`: a reconnect keeps what the *user* wants and drops what the *room* told us. These two are a receipt for "the room has told us where it is", and their issuer goes away on either transition — main stops emitting `remote-state` while we are out of the room and we may come back alone, so a latched flag would eat the saved position on every later episode open.

`disconnected` is not only a terminal state, and the reset is right on every route that reaches it. A mid-session drop that auto-reconnects goes straight to `reconnecting` and never emits `disconnected` on the way (guarded over the whole status array in `syncplay-disconnect-reason.test.ts`, since a tail-only check cannot see an intermediate one), but `handleError()`'s ban/version/password branch and `failHandshake()` on a failed reconnect attempt both do emit it mid-session — and both have run `tearDown()` by then, so main has already dropped its own session state.

`markProgrammaticSeek(target)` (#239) is the seek-side counterpart, and after the 1500 ms window stopped gating seeks it is the *only* thing keeping the app's own `currentTime` writes off the wire — an escaped one is room-dragging, since the reference server's `forcePositionUpdate` sets **every** watcher's position (and `Room.getPosition()` takes `min()` over watchers, so even a `doSeek: false` stale position pulls the room back). All seven programmatic sites arm it immediately before the write:

- `use-mse-player.ts` — the resume-from-middle land on the first append that exposes the buffer, and only when the land actually writes.
- `PlayerView.vue` — `resumeFromSavedPosition`, the quality switch's `savedTime` restore, both translation-switch restores (local-file and stream), and the two episode-nav `currentTime = 0` writes.

The user's own paths (`seek()`, the scrubber's `commitSeek`) deliberately do not arm it. These marks are value-agnostic because the three `savedTime` restores run in a `nextTick` after the source changed, so the write lands on an element at `readyState 0` with an empty `seekable`: it becomes the *default playback start position*, fires no `seeked` then, and is clamped into `seekable` once metadata arrives — a value-keyed mark would mismatch exactly when the new release is shorter than `savedTime`, and broadcast a `doSeek` at the clamped position with no intent behind it.

The `markProgrammaticPlayback` rule — *only flag a call that will actually change the element* — applies here too, and the seek side enforces it inside `markProgrammaticSeek` rather than at the seven call sites, so an eighth cannot forget it: a write to the position the element already reports is dropped without arming. That case is not hypothetical, it is the normal one for the two episode-nav rewinds. They run in a `nextTick` that fires *after* the `src` rebind, so the element has already run the load algorithm and sits at `readyState 0` with the playhead at 0; `currentTime = 0` there only sets the *default playback start position*, which fires no `seeked` then and — being zero — is not seeked to when metadata arrives either. Arming unconditionally therefore latched the mark for the full 15 s TTL and swallowed the user's next real seek, which in the commonest flow (next episode → OP → Skip OP) is the very #239 defect, at a different site. The same rewind on the MSE/remux path still arms, because `mseSrcUrl` has not been rebound yet and the element holds the old source at a non-zero position, so the write really does seek. The residual latch is a write that moves the element but whose `seeked` never arrives (an aborted load); the TTL bounds it, and a retraction path must not be added without a test.

The guard's premise — *a write to the position the element already reports fires no `seeked`* — holds at `readyState 0`, which is where five of the seven current sites write: the restores/rewinds, behind the `src` rebind. It is not true in general: the HTML seek algorithm has no same-position early-out, so at `readyState >= HAVE_METADATA` a same-value write still queues `seeking`/`seeked`. An eighth site arming from a *loaded* element would see that `seeked` arrive unmarked and go out as intent at the position we are already at, which `forcePositionUpdate` then pushes to every watcher.

The other two current sites are post-metadata, and safe for their own reasons rather than this one. The MSE land runs from `onSourceBufferUpdateEnd` under `sb.buffered.length > 0`, by which point MSE's init-segment-received algorithm has already taken the element to `HAVE_METADATA`; it is safe because its strict `t < resumeLandTarget` makes a same-value write unreachable at any `readyState`, which is the stronger property. `resumeFromSavedPosition` runs behind `readyState >= 1` (else on `loadedmetadata`) and is gated on `saved.position > 5` while the element sits at 0, so the two cannot coincide. The condition is deliberately *not* narrowed to `&& v.readyState === 0`: that re-opens the 15 s latch on any engine that short-circuits a same-value seek without firing events, and swallowing the user's real seek is the failure this guard exists to prevent, where a redundant update at our own position is not.

**Known residual — the single marker slot.** `appliedSeekPosition` holds one mark, and every arming site writes it, so any second write in flight clobbers the first and the `seeked` already queued for it escapes as intent. Two shapes:

- Two remote seeks in quick succession. Main's belt does *not* reliably cover this one: `lastAppliedRemotePosition` is re-armed on every inbound remote state, so after the second apply it holds the second target and compares the escapee against the wrong value.
- A mark of one kind clobbering the other — e.g. a remote apply lands while the MSE resume land runs. The apply's echo is consumed by the value-agnostic `markProgrammaticSeek` mark (which matches anything), the slot clears, and the land's own `seeked` then escapes. Main's belt misses this one too, for a different reason: `lastAppliedRemotePosition` holds the apply position while the escapee reports the land target.

Both accepted rather than designed around — the element aborts an in-flight seek when a second write supersedes it, so the window is only an already-queued event, and the escaping position is one the room or our own resume point published moments earlier.

**Both directions of the ping exchange (#231).** Outbound, each `State` stamps `clientLatencyCalculation = now / 1000`; the server echoes it back in its next `State` and we derive `serverRtt = now − lastClientLatencyCalculation` (windowed to `> 0 && < 5`), then shift inbound remote positions by `+ serverRtt / 2` before applying **only while the room is playing** (#235), to account for wire delay. Inbound, the server's own `State` carries *its* `ping.latencyCalculation`, which we echo back on our next outbound `State` so it can measure the same round trip in its direction. Without that echo the server substitutes `0`, its `receiveMessage()` returns immediately, and its RTT and forward delay stay pinned at `0` — so the position we report is stored un-aged by the wire delay and can propagate to the whole room through its `min()` over watchers.

The echo is governed by two mechanisms that carry **different guarantees and fail differently** — neither is redundant, and a reader tempted to delete one as duplicated work should read this paragraph first:

- **Hold-time correction ⇒ the number the server gets is a network RTT.** Our sends are timer-driven, not reply-driven, so we hold the server's timestamp for up to a heartbeat before it goes back out. We therefore echo `latencyCalculation + (now − arrivalTime)` in seconds, **deliberately not a verbatim server timestamp.** Echoed verbatim, the server bills our heartbeat phase to the network — its `_rtt = time.time() − timestamp` has no upper bound — and a ~50 ms link yields ~0.7 s of phantom forward delay pushed onto our position. The reference *client* does echo its local copy verbatim, but only because it replies in-line inside `handleState()` and so has no hold to subtract; the reference *server* solves the mirror-image problem exactly the way we do, echoing our stamp plus its own `processingTime`. The arithmetic is hold-independent: the server computes `now − (ts + hold) = d1 + d2` whatever the hold was. Units are load-bearing — the inbound value is `time.time()` in **seconds**, the hold is a `Date.now()` difference in **milliseconds**, hence the `/ 1000`.
- **Consume-once ⇒ one sample per measurement.** `consumeServerLatencyEcho()` clears the stored pair unconditionally, so one server timestamp is echoed exactly once; every outbound `State` sender must build its echo through that one helper so the guarantee holds across senders. This is duplicate-sample suppression, *not* poison prevention: with the correction in place a re-echoed timestamp is arithmetically correct, merely derived from an old measurement, and N copies of it would feed the server's `0.85` moving average as correlated samples — during exactly the windows where it has the least fresh information (the two 1 Hz timers drift against each other, and the server goes silent during a forced-update window while our heartbeat keeps firing). One echo per inbound `State` is also the faithful translation of the reference client, which is inherently 1:1.

If the correction regresses, the consume-once test still passes and the wire carries a plausible-looking but inflated RTT; if consume-once regresses, every value on the wire is correct and only the server's averaging is over-weighted. Neither test covers the other's failure.

The timestamp/arrival pair is written together on every inbound frame carrying a numeric `latencyCalculation` — recorded above `handleState()`'s playstate guard so a ping-only frame still refreshes it, and type-guarded so a malformed frame leaves a good value untouched rather than parking a string for the next echo. A newer `State` overwrites both halves; updating the timestamp without the arrival time reports the wrong hold. The hold is sanity-windowed at `0 <= ms < 5000` — zero-inclusive, unlike the inbound `rtt > 0` guard, because a same-millisecond hold is the most accurate sample the client can produce. Out of that window the pair is **dropped and no key is sent**, never echoed verbatim: `Date.now()` is a wall clock, and a verbatim echo off a stepped clock hands the server a positive, plausible RTT inflated by up to a heartbeat, which its own guard (negatives only) cannot catch. A missing key is benign — the server substitutes `0` and holds its last forward delay. Residual not closed by the window: a *forward* clock step smaller than it makes `ts + hold` overshoot the server's clock, parking a negative RTT that it hands back out; a monotonic hold source would close that and is deliberately out of scope.

**The shift is gated on `paused` (#235).** A playing position has aged in flight, so `+ serverRtt / 2` is the correction for that; a **paused** position does not advance with wall time, so there is nothing to correct for and the shift is pure error. It mattered most on the paused-**seek** path, because `doSeek` bypasses the apply rule's 3 s tolerance below: a peer scrubbing a paused room used to land everyone else up to 2.5 s (half the `rtt < 5` acceptance window) ahead of where they seeked, with the toast naming a timestamp nobody chose. The reference client gates on the same flag (`updateGlobalState`, `client.py:459-460`; mirrored server-side in `_updatePositionByAge`). The compensated value is computed **once** and read twice — emitted to the renderer *and* stored as `lastAppliedRemotePosition` for the echo guard above; splitting the two re-arms the #220 self-seek loop on any link with `serverRtt > 1 s`. Smoothing the estimate itself (upstream keeps an EWMA forward delay rather than a raw `rtt / 2`) is not implemented.

## Room List Polling (#221)

A **separate** 15 s `setInterval` re-sends the handshake's `{List: null}` for as long as the session is `ready`. Deliberately not a modulo counter inside the 1 s heartbeat: that timer is latency-sensitive, and coupling the two would make the poll cadence drift with it.

Why it exists: `Set: {user}` broadcasts only carry changes that happen while we are connected, so the roster is a cache with one fill point and no refresh. A frame lost to a mid-reconnect gap, a peer that died without a clean disconnect (no `left` frame is ever generated), and a peer the server moved into our room (`RoomManager.moveWatcher` re-broadcasts nothing, so they render with no file line and no **Join & watch** button) all persist until the user disconnects and reconnects.

What makes a repeated full-roster replacement safe lives in `handleList()`:

- **Emit on change.** The rebuilt roster is compared against the previous one and `room-users` is skipped when nothing changed — otherwise a steady room costs four broadcasts a minute forever, each one a fresh array into the store and another run of the renderer's ready-gate watcher. The comparison is **by username**, never by array position: `handleList` builds in `Object.entries` order and appends self at the tail, while `handleSet` appends a joiner and `absorbRemoteFile` appends an unknown user, so the same membership carries different orderings depending on how it was assembled. `JSON.stringify` is wrong for that reason plus key-order and `undefined`-vs-absent differences between the two assemblers, and `animeDlAppMeta` must be compared **by its four scalars** — `extractAppMeta()` returns a fresh object on every reply, so a reference compare is false every time and silently degrades back to emit-always with a green test. On equality the **previous array is kept** rather than reassigned, so an order-only difference cannot leave main and the renderer holding different orderings.

Peer `isReady` is adopted **verbatim**, in both directions. An earlier revision of this feature ratcheted it — a poll could clear a peer's not-ready but never introduce one — because readiness had no push channel, so a poll allowed to *engage* the gate would have made the release wait for a poll too. #229 added that channel, and on the same ordered connection the later frame always carries the newer value, so a poll cannot resurrect a superseded state. Ratcheting after #229 would be a straight loss: a peer the poll discovers mid-buffer (the `moveWatcher` case above) would seat `undefined` and render green with the gate open, where verbatim adoption seats `false` and the next broadcast releases it in milliseconds.

The poll synthesizes no `joined` / `left` room-events: those stay driven exclusively by real `Set.user.event` frames, or a poll landing between a `Set` and its emit would double-toast and a poll after a reconnect would replay every member as "joined". Self-readiness stays authoritative locally — the local user's `isReady` is overwritten from `ownIsReady` after the per-entry loop, so a server value that has not caught up to the last `set-ready` can never clobber ours.

Cost: the reply is **not** room-scoped. The default `RoomManager` builds it from every watcher on the server (only `--isolate-rooms` narrows it to the caller's room), plus one dummy row per empty persistent room, and we keep one room and discard the rest — so on a busy public server it is O(all users), which is what sets the interval at 15 s rather than something tighter. Server-side `handleList` is `@requireLogged` and does nothing but re-send; there is no throttle or quota in the reference server, and the reference client itself polls once per file change.

## Apply Rule

On inbound `State`, the renderer compares remote vs. local:
- `paused` differs → call `play()` / `pause()`.
- `state.doSeek === true` **or** `|remote.position − local.currentTime| > 3.0` → set `currentTime = remote.position`. The 3 s tolerance prevents drift jitter from causing constant micro-seeks.

**The remote position is written unclamped, by design (#226/#240).** `growingFile.clampSeekTarget` is deliberately *not* consulted: the reference server takes a room's position to be the `min()` over its watchers and re-broadcasts it every second with `setBy` naming the laggard, so reporting a frontier-shortened position would be an unsignalled room seek — no `doSeek`, no marker on either side to suppress it — repeated at 1 Hz by the snapshot heartbeat for the whole catch-up. On a growing `.part` the element instead seeks to the room's position and stalls there (the protocol handler advertises the full `totalBytes` denominator and serves a past-the-frontier range from the growing tail stream), which fires `waiting`, reports us not-ready and makes the room wait for us. Clamping what *we* initiate stays right; clamping what the *room* initiates is what drags peers backwards.

**Below `HAVE_METADATA` the apply is deferred, not dropped (#240).** `applyRemoteState` splits in two:

- The **bookkeeping half** (`syncplayLastRemotePlaying`, `syncplayLastAppliedPaused`, `syncplayPausedBy`) runs on *every* inbound state, above the `getVideoEl()` lookup. The old `if (!v) return` dropped it whenever no player was mounted, and `applySyncplayReadyGate()` then acted on a stale play intent the moment one appeared. It is **re-asserted when a parked state is applied**: a local play/pause during the wait overwrites it, and the deferred apply would then pause the element while the bookkeeping still said "the room is playing" — the very next ready-gate pass plays it back, with `syncplayPausedBy` naming nobody. Re-running it costs nothing on the immediate path (`pausedChanged` is already false) and makes a deferred apply re-assert *this bookkeeping* as of the moment we enact it. It does **not** make the whole state current: `state.position` is the one field that goes stale while parked, and it is deliberately left uncompensated. Main shifts a playing room's position by `serverRtt / 2` **once**, at emit time (`handleState`), and nothing advances the parked copy afterwards — so a park that outlives a slow HEVC prep applies a position behind the room by the park's duration. Three things bound that error, which is why the write-time half re-projects nothing: the park is *overwritten* rather than queued, so at the room's ~1 Hz state cadence it is normally under a second stale; an error above the apply rule's 3 s tolerance is corrected by the very next state; and until our position converges main's adoption gate (`isAdopted`, `ADOPT_TOLERANCE_S` = 3 s) withholds our playstate entirely — `sendLocalState()` returns before the wire and `buildPlaystate()` falls through to the spectator mirror, which reports the *room's* projected position and no `paused` — so `Room.getPosition()`'s `min()` can never elect our stale value and no peer is dragged back. The gate is un-latched exactly where a park is reachable: parking needs an element below `HAVE_METADATA`, i.e. a fresh `<video>`, and `setFile()` clears `playbackAdopted` on a file change while `updateSnapshot()` clears it whenever the previous player's snapshot has gone stale (`PLAYBACK_STALE_MS`, 5 s) — this is not the latched-gate hole the echo-ack emitter documents. That same gate is why the pre-metadata `currentTime === 0` snapshot — which this change makes reachable, where the old unguarded write left the getter reading back the remote position — is harmless too. This half is also where a pending user pause is **cleared** (#228), at the top and keyed on `state.paused === true`, then falling through: running for every state, parked or not, is precisely what makes it a placement the element half's early-outs cannot swallow, and the fall-through is what hands the "Paused by you" badge over through the ordinary `pausedChanged` path. Only the badge body is held while a pause is pending; the two mirror writes are not, because their consumers need the room's truth (the gate's `!pendingUserPause` term is what stops the room acting on it).
- The **element half** — the `currentTime` / `play()` / `pause()` writes, plus `effectivePaused`, the no-op early-out, the 1500 ms send window and the `intendedPaused` adoption — runs immediately when `video.readyState >= 1`, and is otherwise **parked** in `pendingRemoteState` and applied from `<video @loadedmetadata>`. No element at all parks the same way. At `HAVE_NOTHING` a `currentTime` write becomes the *default playback start position*: it fires nothing and is silently re-targeted by whatever writes `currentTime` next, which on every episode open is the local resume, the MSE land or a nav rewind — so an early remote position simply lost a race to local state. `readyState >= 1` and not `>= 3`: duration and seekability are all the apply needs. While a user pause is pending and the state says `paused: false`, this half **holds** (#228): the seek block still runs — withholding it would stall `isAdopted()`'s drift latch and turn every hold into the failure toast — while the `intendedPaused` clobber, the *whole* play/pause block and the seek toast are skipped. The whole block, not just the `v.play()`: skipping only the call would latch `appliedPaused = false` with no event left to consume it, and the user's next real play would be eaten as that echo. The seek toast goes because during a hold the element is deliberately behind, so `needsSeek` is true on essentially every apply and "X seeked to …" would describe a seek nobody made. "A playing state was held" is recorded **here, below the no-op early-out** — a state that early-outs moved nothing and so held nothing — which for a parked state means it is recorded at *unpark*, not at arrival.

Everything in the element half is computed at *write* time, never at park time. `effectivePaused` reads the live roster, so a park-time snapshot would resume us over a peer that went not-ready during the wait; `appliedSeekPosition` is armed immediately before the write — with `Math.max(0, state.position)`, the exact number main emitted — because the deferred write fires arbitrarily far outside the wall-clock window and the marker is then the sole guard against its echo reaching the wire. Only the freshest state is ever applied: `pendingRemoteState` is overwritten, never queued, and a superseded state never toasts. A deferred apply toasts late, at apply time.

**Resume precedence: the room outranks the saved position (#240).** One predicate, `PlayerView.roomOwnsPlayhead()` — the session is `ready` *and* `syncplay.hasRemoteStateApplied()` (a remote state is parked, or one has been applied since the last reset) — gates **both** resume paths, because there are two and they move the playhead in different places:

- `resumeFromSavedPosition` skips its `currentTime` write **and the "Resumed at …" toast**. It is `async` and awaits `watch-progress:get`, so without the guard it always lands after the synchronous apply in the same `loadedmetadata` dispatch and overwrites the room's position on every episode open. The toast goes with the resume it describes: announcing a position the playhead is not at is a false statement, and the remote-seek toast already explains the movement. `watchedReported` is still set from the saved record.
- `use-mse-player`'s **initial resume land** is cancelled through the same predicate (passed in as the `hasRemoteStateApplied` dep). On an MSE/MKV session that land *is* the resume — `resumeFromSavedPosition`'s MKV branch deliberately writes no `currentTime` (#198) and only toasts — so guarding the toast alone would leave the rule false on the primary local-`.mkv` path: the apply puts us on the room's position at `loadedmetadata`, then the first media append lands on the saved one. Silently, too — the land arms `markProgrammaticSeek`, so the room never hears the move, and the next 1 Hz state (`diff > 3`) seeks us back: a playhead bouncing room → saved → room and up to two extra ffmpeg respawns, against #240's own "must not increase unbuffered writes". The pending land is **consumed** when cancelled, not deferred: it is a once-per-session affair, and re-arming it would only relocate the same overwrite to a later append.

The flag **must not latch**: main stops emitting `remote-state` the moment we are alone in a room, so it is reset — together with any parked state — on episode/translation switch, on `reconnecting`, and on `idle`/`disconnected`. `reconnecting` is in that list for the same reason as the other two and not because the session ended: we are out of the room while it runs and may rejoin alone. Only the remote-state tracking resets there; `syncplayLastRemotePlaying` and the local-ready flag survive a reconnect. Resetting inside a live room costs at most a sub-second flash at the saved position before the next 1 Hz state seeks us to the room; latching would eat the user's saved position on every later episode open, forever. One accepted consequence: if the guard skips the resume and the parked state is then invalidated (a disconnect mid-open), **the saved position is dropped for that open** — all three `loadedmetadata` registrations are `{ once: true }`, and re-arming a consumed one means a fresh `watch-progress:get` round-trip that can race a newer remote state on reconnect. The position is still stored; the next open resumes normally.

## Readiness Gate (Buffer Sync)

When either user runs out of MSE buffer (HTML5 `waiting` event, or the MSE respawn path's `waitForBufferAhead`), the renderer calls `syncplay:set-ready(false)` which emits `Set: {ready: {isReady:false, manuallyInitiated:false}}`. A user dot turns amber in the popover's member list. Main's `ownIsReady` outlives any one player while the renderer's copy is player-scoped and only pushes on a change, so `setFile()` clears a stale `false`: a player closed mid-buffer would otherwise pin the user as *Buffering* in every peer's roster and hold their ready gate down for the rest of the session. That reset is keyed on the same "a new player is announcing itself" signal as the adoption reset above — `identityChanged || file.newPlayer === true` (#236). Unguarded it fired on *every* re-push, and a re-push landing mid-buffer put `Set: {ready: {isReady: true}}` on the wire while we were still filling, telling peers we were buffered when we were not and releasing their gate. Re-pushes of an unchanged name are routine: `onDurationChange` re-pushes once real duration is known, an in-player translation switch re-pushes a byte-identical `canonicalName`, and the transition-into-`ready` watcher re-pushes on a reconnect landing mid-buffer — and readiness is `false` on exactly those loads. The renderer cannot repair it afterwards: `syncplayLocalReady` starts at `true` and `setSyncplayLocalReady()` returns early on no change, which is why main's reset exists at all.

**Live readiness is a top-level `Set: {ready}` (#229).** Main tracks readiness per user from `Set: {ready: {username, isReady, manuallyInitiated, setBy?}}` — the reference `sendSetReady`, broadcast on join, on room switch and on every toggle — and from `List` messages. It is *not* carried on the `user` path: `sendUserSetting` writes only `room`/`file`/`event`, so the `user[X].isReady` branch main used to have was dead code against a real server and is gone. Three rules govern the parse, and none is defensive:

- **Non-boolean `isReady` maps to `undefined`, never `false`** — the same `typeof … === 'boolean' ? … : undefined` expression `handleList` uses, because it is the same server-side value through a second door. A watcher that has never toggled has `_ready = None`, and `isReady()` returns `None` unconditionally on a `--disable-ready` server, so the join broadcast is literally `{ready:{username, isReady:null}}`. Both roster dots key on `=== false`, so `undefined` renders green; coerced to `false` it would instead give the peer a permanent amber dot and hold `syncplayAllUsersReady()` shut for the whole session. A `--disable-ready` server therefore degrades to "everyone always ready", which is what such a server means.
- **A frame naming *us* re-asserts `ownIsReady`; it is never adopted.** Readiness here is a measured fact, not a preference — its single writer is the renderer's `syncplayLocalReady`, edge-triggered off MSE buffering, and there is no main→renderer path to reset it. `broadcastRoom` has no sender filter, so our own send echoes back with our name on it; an equal value is silent. An *unequal* one is a peer's `setOthersReadiness` (any peer can do this in an ordinary room, and the server **stores** the forced value), and it gets exactly one `sendSetReady(ownIsReady)` back, under `setReady`'s own `state === 'ready'` guard. That guard fires on a normal path, not an exotic one: `handleHello` runs `addWatcher` — which seats us and broadcasts readiness into the room at `protocols.py:558` — *before* `sendHello` at `:560`, so room frames reach us while `status.state` is still pre-`ready`. Nothing is lost by dropping the re-assert in that window, because `finishHandshake()` sends `ownIsReady` unconditionally moments later. Skipping it instead would leave the server serving `false` for us until a buffer flap or reconnect, holding every peer's gate down; adopting it is a dead end, because the roster self row would pause us while the renderer's equality guard stops it ever pushing again. It converges in one round trip: our send omits `username`, so the server takes its plain `else` arm, stores our value and rebroadcasts it — and that echo compares equal. The boolean guard above is load-bearing rather than defensive on this path: `null` can never equal `ownIsReady`, so an unguarded re-assert would be a wire-speed loop. The parse itself is deliberately *not* gated on `status.state` — the join broadcast reaches us before `Hello` — and the self compare is case-insensitive, which is safe because the server's `findFreeUsername` lowercases every live watcher name, so no peer can hold a case-only variant of ours. We deliberately do not advertise `setOthersReadiness` in `Hello`, which is what keeps the server's own "X set Y as ready" chat notice coming — the user's only explanation for the re-assert (#234).
- **A frame naming an unseated username seats nobody.** It carries no room key at all, so seating from it would be a membership write the room filter above structurally cannot gate, and an invented row can carry `isReady:false` and pause us for a member we have no membership evidence for. Nothing is lost: the switch-in that would otherwise need it is seated by rule 1 above (#230), from the bare `{user:{X:{room}}}` frame the server broadcasts one line earlier.

The branch routes through the same `usersDirty` accounting as the `user` loop, so one `Set` produces one `room-users` emit — a second emit would double-fire the renderer's watcher and its ready gate. A *deliberate* peer transition (`manuallyInitiated === true` or a `setBy` present) also writes a room-log line; a presence check on `manuallyInitiated` would not do, since it is present in both branches of the server's `sendSetReady` and the buffer-driven path is exactly the one that sets it `false` — every peer's `waiting`/recovery flap would land in the log the user reads for joins and chat. That truth check is the *whole* condition: the two broadcasts that can carry a `None` readiness (`sendJoinMessage`, `sendRoomSwitchMessage`) both pass `manuallyInitiated=False` with no `setBy` and fail it anyway, and on a `--disable-ready` server no peer ever holds a boolean to move away from, so an extra `isReady !== undefined` clause would be unreachable code no test could kill. The line's wording then keys on `=== false` exactly as the roster dots do, so the one non-conforming frame that could reach it — a peer writing a literal `null` after a boolean was seated — reads "ready" beside a green dot rather than contradicting it.

Renderer gates playback locally: if any room member (including self) is `isReady: false`, `applySyncplayReadyGate()` calls `v.pause()` even when the last remote `State` said `paused: false`. The last remote play intent is remembered in `syncplayLastRemotePlaying`; when the last not-ready user flips back to ready, the gate calls `v.play()` automatically. This keeps two app instances locked together when one falls behind on download/decode, rather than ping-ponging pause/play broadcasts.

**The gate never overrides a pending user pause (#228):** `shouldPlay` is `syncplayLastRemotePlaying && syncplayAllUsersReady() && !pendingUserPause`. The flag is honored **at the action, not at the variable** — suppressing the mirror write that feeds it would falsify the room intent every other consumer reads, and would flip the gate's own *pause* branch against the user's later resume. This is the second of the two resume paths a pre-adoption pause used to lose to, and the more persistent one: the gate is re-entered on every readiness flip and every `room-users` emit, so without this term the pause is undone on the next buffer refill even if no state ever applies.

## Remote Episode Auto-Nav

When the remote user advances to a new episode (detected by `features.animeDlAppMeta.episodeInt` change on inbound `Set.file`), main broadcasts `syncplay:remote-episode-change` with `{ animeId, episodeInt, translationId }`. PlayerView checks `animeId` against its current anime:
- **Match** — walks `goToEpisode('next'|'prev')` in a loop until `activeEpisodeIndex` reaches the target. Reuses the normal episode-switch path (including translation resolution).
- **Mismatch or episode not in list** — toast only. The app can't navigate to an anime that isn't loaded in the current view.

## Join Flow (WatchTogetherView, #213)

**Roster (#220):** membership comes from two sources, and only one of them arrives unasked. The server *broadcasts* `Set: {user:{X:{room, event?, file?}}}` for changes that happen while we're connected, but people already sitting in the room generate nothing — so `finishHandshake()` sends `{List: null}` to request the full roster (and re-requests it on every reconnect, which is how membership resyncs after a drop). Without that request a joiner saw "Room is empty — you're the first one here" in a room with people in it. The `List` reply is keyed by room and covers **every room on the server**, so `pickOwnRoom()` takes only ours — by the name the server seated us in (`handleHello` adopts a canonicalized `room.name`), falling back to the sole entry when the payload has exactly one and — provided that entry is an object (#257, below) — **adopting that entry's key** into `config.room` *and* `status.room`, so the roster, the `Set` filter below and the name the view renders all key off one string (`pickOwnRoom()` is a mutator on that arm despite the name — `status.room` is the copy `WatchTogetherView` shows, and every later `setStatus` that carries a room reads it back off the config, so leaving it stale would flip the displayed room on the next reconnect). If neither arm yields an object — our room key is absent *and* the payload holds some number of rooms other than one — `handleList` logs the room name and the payload's keys under `SYNCPLAY_DEBUG` and **returns without touching the roster** (#223), rather than falling through to seat the local user alone and emit: a payload we cannot key is not evidence that the room emptied, and the fall-through blanked every peer and rendered "Room is empty — you're the first one here" in a room that is not. Without the guard this would be a roster that flaps to empty and back on a timer, now that #221 re-requests the roster every 15 s rather than once per handshake. Only the *non-object* case skips: an object entry stays authoritative even when empty, or a room that genuinely empties would never clear under that poll — a freeze with no self-repair, strictly worse than the wipe. The other half of that trade is upstream (#257): `pickOwnRoom()` used to adopt a single-room payload's key *before* this guard could reject the entry, so a non-object sole entry — `{"ghost-room": null}` — kept the roster here and still rewrote `config.room`/`status.room` on the way in. That is the one shape where "keeping the roster is safe" did not hold: the `Set` filter below keys off `config.room`, so the next genuine in-room `Set: {user}` read as off-room and rule 2 evicted the peer as a leave, and recovery then depended on the shape of the next poll: a reply carrying ≥2 rooms — the usual one, since it covers every room the server knows — missed on both arms and landed back on this same `return` every tick, and a reconnect only made the ghost name authoritative (the `Hello` re-sends `config.room`) rather than undoing it; a single-room reply keyed `cinema` re-fired the fallback and self-healed within one tick, losing only the `Set` frames inside it; and a reply that still carried `ghost-room` as an *object* was worse than either, resolving through `hasOwnProperty` and seating that room's members as ours — the stranger-seating #230/#242 exist to prevent. The adoption is therefore gated on `isObject(entry)`, ahead of **both** writes, and it is deferred rather than abandoned: the next reply whose sole entry is usable adopts exactly as before, so a server that canonicalized our room out from under us is not locked out by one unreadable reply. It also restores the debug log above, which prints `config.room` and would otherwise name the adopted room rather than the one we joined. `handleList` and `Set.file` share `extractAppMeta()`: a peer whose `animeDlAppMeta` doesn't survive the parse is listed but gets no "Join & watch" button, so both paths must read it identically. The roster's file shape differs from the broadcast's in one place: the server writes `file: {}` — never null, never absent — for a watcher with nothing loaded, so `handleList` maps a nameless file back to `null` (the `Set` path omits a falsy file and can't reach it).

**Room scoping on the `Set` path (#230).** With `isolateRooms` off — the reference server's default — `Set: {user}` is broadcast to *every* room on the server, so `handleSet()` filters each `user[X]` entry against `config.room` before acting on it. The filter is **ordered**, not a flat "ignore other rooms", because a peer switching out reaches us as a lone entry naming their **destination** with no `left` event (the server moves the watcher before broadcasting the switch):

0. **Self is exempt** — never filtered, never skipped. Our own file push is echoed back to us without sender exclusion, and `absorbRemoteFile()` is what keeps our roster row's file current between `List` replies. A self entry naming another room is not something a reference server can emit, so it is ignored rather than adopted (see [#230](https://github.com/mikkerlo/anime-downloader/issues/230) for the adopt-and-re-`List` design held in reserve).
1. **Room absent or equal to ours** — processed as before. Additionally, an entry carrying a room but neither `event` nor `file` is a switch *into* our room: the peer is seated and announced. The `file` exclusion matters — `sendFileUpdate` also emits `{room, file}` with no `event`, on the hot path, and `absorbRemoteFile()` already announces `X switched to "…"` and owns the seating there. (There was a third exclusion for `isReady`, to keep this from announcing in front of a per-user readiness branch further down the loop; #229 deleted that branch — readiness is a top-level `Set: {ready}`, never a `user` key — and the exclusion with it, so a stray `{room, isReady}` from a proxy is now seated as the room-only frame it is, with the key ignored.)
2. **Room differs and we have the user seated** — the switch-out frame: remove and emit `X left the room`. Runs *before* the `file` branch, or a frame carrying both would re-seat the user it just removed. This is also what keeps a peer's last live readiness from outliving its membership: after #229 a peer that switched away mid-buffer would otherwise leave an `isReady:false` behind and pin our ready gate.
3. **Room differs and the user is unknown** — the whole entry is dropped, `file` included.

The comparison **fails closed**: `config.room` is a `string`, so an undefined own room means `this.config` is null, and every room-carrying entry then reads as off-room rather than as "no filter". No frame can actually arrive without a config — both sites that null it (`failHandshake`, `disconnectInternal(true)`) go through `tearDown()` → `resetTransportState()`, which clears `rxBuffer` and so truncates the rest of the chunk mid-drain, and `tearDown()` strips the socket's listeners besides — but the comparison is written so that if that invariant ever breaks the failure mode is dropping peers, not seating strangers.

There is deliberately no top-level `Set: {room}` handler: that field is a client→server command, and honouring an unsolicited one would rewrite the filter's reference name mid-session and re-expose every stranger. `handleHello` is the only place a room name is adopted from the server, plus `pickOwnRoom`'s fallback above.

A dedicated **Watch Together** sidebar view lets a user join a room *before* opening the player. It connects with the saved server/username settings, renders the live member list (username, ready dot, current file) from the `useSyncplayStore` Pinia store, and — for members whose `Set.file` carried `animeDlAppMeta` — offers **"Join & watch"**: the room state is re-fetched at click time (the peer may have advanced episodes), then `useOpenEpisode` resolves the anime + a CDN stream for the peer's `(animeId, episodeInt, translationId)` and opens the built-in player. mpv/VLC peers (no app metadata) are listed but not auto-joinable.

Connection handoff: the room connection lives in main and outlasts view mounts. `useSyncplayClient` never assumes it owns the lifecycle — on mount it re-seeds the store and, if the session is already `ready`, immediately pushes the current file (the transition-into-ready watcher never fires in that case; without the push the joiner would stay invisible to the host). `onDurationChange` re-pushes once real duration is known.

Renderer state ownership: `useSyncplayStore` (`src/renderer/src/stores/syncplay.ts`) singleton-owns the `connection-status` and `room-users` subscriptions, seeded from `syncplay:get-status`/`syncplay:get-room-users`; WatchTogetherView and the player's `useSyncplayClient` both read from it. Player-scoped subscriptions (remote-state, room-event, trace, remote-episode-change) stay in `useSyncplayClient`.

## IPC Surface

Main-side handlers (see [IPC Handlers](./ipc.md)): `connect`, `disconnect`, `set-file`, `local-state`, `local-snapshot`, `set-ready`, `get-status`, `get-room-users`, `set-password`, `has-password`. Broadcasts: `connection-status`, `remote-state`, `room-users`, `room-event`, `remote-episode-change`. Settings tab "Watch Together" in `SettingsView.vue` persists host/port/room/username/autoReconnect under the `syncplay` electron-store key, and the password separately under `syncplayPassword` (see Password ownership above). The live connection itself is **not** persisted: users must rejoin after a restart.

Debug tracing gated by `SYNCPLAY_DEBUG=1` env var — dumps every inbound/outbound JSON message and state transition to the main process log.
